Security

From a strict security perspective, Qubes OS is not reliable

Written by FlyWithMe (a SimpleX chat user) - Updated August 16, 2026

This critique evaluates Qubes OS through Xen, dom0, device domains, hardware trust, recovery, and total trusted computing base. It recognizes the value of compartmentalization while explaining where shared hardware and privileged infrastructure limit that model.

1 - Xen hypervisor

Qubes OS runs its domains on Xen, a type-1 hypervisor. Xen enforces memory and CPU isolation, while dom0 holds administrative authority over the domains. This creates a strong boundary for ordinary guest compromise and a concentrated failure point: code execution in Xen can invalidate every domain boundary enforced by that Xen instance. Firmware, microcode, and speculative-execution flaws sit below the same boundary.

On Intel VT-x, Xen executes in VMX root mode while guest kernels run in VMX non-root mode; AMD-V provides the corresponding host and guest modes. Ring numbers describe privilege inside each mode and do not by themselves rank security. Xen's authority comes from controlling second-stage memory translation, interrupts, virtual CPUs, and the interfaces presented to guests.

Current Qubes releases use PVH by default for qubes without assigned PCI devices and HVM for qubes that require PCI assignment. PVH combines hardware-assisted CPU and memory virtualization with paravirtualized I/O; HVM presents a fuller hardware model. Both modes expose guest-controlled input to Xen and backend components. The relevant security comparison is the code and interfaces reachable in each mode, not a blanket claim that HVM is safer than paravirtualization.

Windows qubes use HVM, but Windows is not the only Qubes workload using hardware-assisted virtualization. The previous claim that most Qubes templates use legacy PV and that only Windows receives hardware assistance is obsolete.

Full virtualization presents emulated hardware and lets a guest run without paravirtualized kernel changes. It does not make the guest fully isolated: the hypervisor and device model still parse guest-controlled state. Hardware-assisted implementations include KVM, Hyper-V, VirtualBox, and OpenBSD vmm.

Several attacks on Qubes OS originate in an AppVM, and some historical exploits have used Xen vulnerabilities to escape the guest and compromise Dom0 or other VMs. However, not all attacks go through Xen; there are also vectors via firmware (ME/PSP), drivers, IOMMU, or flaws in dom0 and service qubes. dom0 is decisive because it manages the domains and administrative policy. Qubes issue 4551 proposed OpenBSD support for dom0 or guests, but replacing Linux in the control path would require porting Qubes' Xen tooling, GUI, qrexec, packaging, and management integration rather than changing one template.

https://github.com/QubesOS/qubes-issues/issues/4551

Qubes users also proposed OpenBSD for the network domain to reduce reliance on the Linux network and driver stack. The proposal identified substantial integration and hardware-support work rather than an immediately supported replacement:

https://github.com/QubesOS/qubes-issues/issues/5294

A community guide demonstrates an OpenBSD-based sys-net configuration, but the guide is dated and Qubes does not list that configuration as an officially supported NetVM. Its current compatibility with every Qubes networking and device workflow is undocumented:

https://forum.qubesos.org/t/fortifying-sys-net-a-shift-to-openbsd/31973

Changing a network domain does not remove Xen, dom0, qrexec, virtual devices, firmware, or the IOMMU from the shared trust model. Running OpenBSD directly on hardware omits the guest-to-hypervisor interfaces that appear when it runs as a VM. Dom0's lack of network access removes a major remote entry point, but dom0 still processes selected guest-influenced data through administrative services.

A compromised NetVM has limited authority by design, but it can attack the Xen and backend interfaces exposed to that domain. A second exploit against a shared privileged component can then cross into dom0 or other domains. Hyper-V uses a different hypervisor, root-partition, device, and update architecture. Raw CVE totals do not establish that it is safer than Xen; a valid comparison requires affected configurations, reachable components, severity, mitigations, and patch latency.

The argument I see most often from Qubes OS developers is dismissive: "A hypervisor escape is rare," "these attacks are difficult to carry out," or "you have no reason to worry about it." That misses the point entirely. Xen has accumulated hundreds of published XSAs (Xen Security Advisories) since its inception, many of them critical, including numerous guest-to-host escape vulnerabilities. By comparison, KVM and Hyper-V have had far fewer escape-class vulnerabilities in the same period. Hypervisors still benefit from a kind of security by obscurity, because most commodity malware does not expect to be running inside a VM and therefore does not bother attacking the hypervisor.

If this model becomes more popular (and it is), attackers will have more reason to target hypervisors, especially Xen. Qubes OS also does little to hide the fact that a guest is virtualized, which makes this problem easier to recognize from inside a VM. That brings us to the next issue.

2 - Lack of VM spoofing

In most VM setups, guest systems can easily detect that they are virtualized. On Windows, this can be visible through registry keys, drivers, processes, and other system artifacts.

An example of this fact is that when using both Windows and Tails (Linux) in a virtual machine, you will receive a notification from the guest OS indicating that the system is being virtualized.

This is why Tails warns you when it is running inside a virtual machine

https://tails.net/doc/advanced_topics/virtualization/index.en.html

This can be masked. There are many scripts and tutorials that try to hide virtual machine presence from the guest, and on Linux this can be easier because the user has more control over the environment:

  • https://github.com/sammwyy/NoVM
  • https://github.com/Batlez/CloakBox
  • https://forums.virtualbox.org/viewtopic.php?t=112808
  • https://github.com/d4rksystem/VMwareCloak

Qubes OS does not try to do this kind of concealment, so malware can detect the VM context early and adapt its behavior, or an attacker with remote access may, upon realizing that they are in a virtualized environment, seek to exploit the hypervisor.

Qubes already modifies its template images, so reducing exposed virtualization fingerprints is technically feasible. The project could define and test a supported anti-fingerprinting profile instead of leaving each template to disclose the environment independently.

3 - Linux-based attack surface

Qubes OS uses a Fedora-based dom0 and standard Linux kernels. My argument is that this inherits Linux and Fedora risks, and does not automatically give users a stronger baseline than a well-hardened non-Qubes system.

Dom0 uses a Fedora-derived userland, but Qubes controls its package set and supplies security-critical updates independently of the base Fedora release lifecycle. My criticism is narrower: dom0 still inherits a large Linux and Fedora codebase, while its privileged Qubes services require their own review and update path. That baseline does not include every hardening policy supplied by projects such as Secureblue.

A compromised sys-net does not automatically expose memory from other qubes; Xen and the IOMMU are intended to prevent that access. Memory corruption in Xen, a backend, or an IOMMU-facing path can defeat the boundary. The prevalence of memory-safety bugs in large C and C++ codebases makes those privileged parsers a legitimate target, but an ecosystem-wide percentage does not prove a specific Qubes flaw.

See my other article proving this: The C language and its biggest problem: evidence of its insecurity.

Compartmentalization contains a guest only while Xen, dom0, device domains, and their communication interfaces preserve the boundary. A flaw in any privileged component can bypass the separation presented to the desktop user.

Qubes must combine isolation with hardening inside each Linux domain and in privileged components. Relevant controls include FORTIFY, PIE, RELRO, kernel self-protection, reduced privileged executables, and enforceable mandatory-access-control policy. Fedora templates support SELinux, but Qubes does not make one strict domain policy universal across every template and service role.

Fedora Secureblue supplies a defined Linux baseline: hardened kernel arguments, restricted user namespaces, mandatory-access-control policy, reduced privileged executables, and disabled services. Qubes' isolation model does not automatically provide those controls inside each Linux domain.

4 - Operational complexity

Qubes OS requires users to manage templates, disposable templates, domain labels, qrexec policy, update paths, device assignment, network chains, and storage semantics. Each relationship adds policy state that can be misread or configured inconsistently.

Qubes ships restrictive defaults for domain separation, but safe operation still depends on template maintenance, qrexec policy, device assignment, and correct placement of data and applications. The architecture cannot infer those user-specific trust decisions.

Complexity is not identical to attack surface, but every privileged parser, policy edge, and state transition adds behavior that must be implemented, reviewed, and operated correctly.

5 - Systemd attack surface

Systemd expands the Linux service-management surface through units, sockets, timers, logging, IPC, user sessions, and supporting daemons. systemd-analyze security reports service sandbox settings, although its score evaluates selected unit properties rather than the security of the complete service. Qubes templates do not inherit every systemd hardening choice made by Secureblue.

Systemd centralizes responsibilities that smaller init and rc designs keep separate. Its own project structure groups them into five layers:

  • 4. systemd Utilities
  • 2. and 3. systemd daemons and systemd targets
  • 1. systemd Core
  • 0. systemd Libraries (the base)

Each layer contains programs and libraries that parse configuration, messages, credentials, or service state. The security cost comes from those reachable interfaces and privileges, not from the layer count alone.

The following sources present broader criticism of systemd's scope and integration:

  • Critical views on systemd:
    • https://nosystemd.org
    • https://ihatesystemd.com
  • Suckless developers on systemd: http://suckless.org/sucks/systemd/
  • Broken by default: http://ewontfix.com/14
  • The world after systemd: https://the-world-after-systemd.ungleich.ch

Official templates without systemd would let users choose a smaller service architecture inside guest domains. Replacing systemd in dom0 is a separate engineering task because Qubes management packages and service integration target the supported Fedora-based environment.

6 - Hardware support and compatibility problems

Qubes OS hardware compatibility is narrow in practice. Effective device isolation requires working IOMMU support, current Qubes releases require SLAT, and Xen, Linux, firmware, and individual devices must all work together. Anti Evil Maid (AEM) narrows the compatible set further because its current design requires TPM 1.2 and Intel TXT.

https://www.qubes-os.org/hcl

Closing that gap requires coordinated work across firmware, Xen, Linux drivers, and Qubes integration.

Users outside the certified list must verify every security-relevant requirement on the exact configuration: IOMMU, SLAT, virtualization, device assignment, suspend behavior, firmware updates, and current CPU microcode. Missing microcode support leaves some processor vulnerabilities without the vendor mitigations on which Qubes and Xen depend.

Pay attention to what the developers themselves say on the official website:

There is a class of security vulnerabilities that can be fixed only by microcode updates. If your computer or the CPU in it no longer receives microcode updates (e.g., because it is too old), it may not be possible for some of these vulnerabilities to be mitigated on your system, leaving you vulnerable.

Qubes OS depends directly on CPU virtualization features such as Intel VT-x, Intel VT-d, AMD-V, and AMD-Vi. Its isolation model therefore includes proprietary processor microcode and hardware behavior in the trusted computing base. Vulnerabilities in that layer affect Qubes directly.

Qubes code cannot compensate for every defect below Xen. Intel and AMD engineering, disclosure, and microcode support are prerequisites for the isolation guarantees that Qubes builds above them. This privileged dependency is central to the design, not an optional peripheral component.

Qubes OS's short certified-hardware list reduces the number of configurations the project must test, but it also concentrates buyers on a limited set of vendor supply chains. The resulting concentration is an architectural risk inference, not a documented purpose or demonstrated compromise of Qubes vendors. Operation Trojan Shield illustrates the broader threat model: the FBI distributed an advertised secure phone through a controlled company and used it to collect criminal communications.

https://www.justice.gov/usao-sdca/pr/fbi-s-encrypted-phone-platform-infiltrated-hundreds-criminal-syndicates-result-massive

Qubes also depends directly on Intel or AMD virtualization extensions and their microcode. A defect in that common layer can bypass protections above it across every affected Qubes installation. This does not prove that Qubes is categorically the operating system most vulnerable to supply-chain attack; it identifies a concentrated dependency that a nonvirtualized Linux or BSD installation does not place at the center of its isolation model.

The Fedora-based dom0 adds another privileged software supply chain. Qubes signs dom0 packages and routes downloads through an UpdateVM, so compromise of a Fedora mirror alone does not authorize a malicious update. Compromise of a trusted signing key, build system, or accepted privileged package remains system-wide. My objection is precise: a compartmentalized desktop still has centralized producer and signing dependencies at its most privileged layer.

7 - Anti Evil Maid and TPM 1.2 requirements

Qubes OS itself does not require a TPM. Its optional Anti Evil Maid (AEM) package requires a TPM 1.2 interface and a working Intel TXT engine; it does not use TPM 2.0. AEM detects selected changes to the measured boot chain. It does not prevent every physical attack, and a Qubes installation without AEM can still use disk encryption and physical controls.

https://doc.qubes-os.org/en/latest/user/security-in-qubes/anti-evil-maid.html

AEM adds a dependency on TPM 1.2, Intel TXT, firmware, and a separate boot-time security workflow. That adds proprietary code, operational complexity, and more ways for misconfiguration to break boot or weaken security. Firmware or vendor bugs in the TPM or Intel TXT chain can become a persistent compromise point and can subvert the measurements AEM relies on.

Published TPM and firmware vulnerabilities require vendor updates. Hardware that has left vendor support cannot receive those fixes, so the useful lifetime of AEM also depends on continued firmware and microcode maintenance.

A TPM contains a device-specific endorsement key (EK), whose private portion is designed not to leave the TPM. Certificates or attestation records linked to that identity can still enable device correlation; attestation keys and privacy mechanisms exist to avoid exposing the EK directly. This is a real privacy and trust dependency, but it is not evidence that a TPM is itself a backdoor.

AEM specifically requires hardware and firmware that ordinary users cannot meaningfully audit. Alternatives such as owner-controlled firmware, verified boot, detached secrets, tamper evidence, and strict physical custody address parts of the same threat model, but none is a drop-in replacement with identical guarantees. AEM's documented design chooses measured launch through TPM 1.2 and Intel TXT, with the code, compatibility, and vendor dependencies that choice entails.

More on this topic from an authority in the field: https://inv.nadeko.net/watch?v=t1eX_vvAlUc

Qubes security guidelines dictate that USB devices should never be attached directly to dom0, since this can result in the entire system being compromised. However, in its default configuration, installing and using AEM requires attaching a USB drive directly to dom0.

The installation path conflicts with Qubes's normal rule that USB devices must not be attached to dom0. Attaching an untrusted USB device exposes the most privileged domain to its controller and input, so the AEM documentation presents this as a security trade-off rather than a safe default.

(The other option is to install AEM to an internal disk. However, this carries significant security implications, as explained here.)

Installing AEM from USB temporarily accepts a dom0 exposure in order to establish later boot measurements. Installing it to an internal disk avoids that USB path but introduces the separate implications described by the project.

This presents us with a classic security trade-off: each Qubes user must make a choice between protecting dom0 from a potentially malicious USB drive, on the one hand, and protecting the system from Evil Maid attacks, on the other hand.

I consider that trade-off too costly. A physical-attack defense should not require a privileged USB installation step that the same security model tells users to avoid.

8 - Intel ME dependency

Devs: If you cleaned your Intel Management Engine with e.g. me_cleaner while installing coreboot (or libreboot) then you are out of luck. For now you have to choose between cleaning your BIOS and deploying Anti Evil Maid.

AEM's Intel TXT requirement also makes it incompatible with systems whose Management Engine firmware has been sufficiently disabled by tools such as me_cleaner. That is a documented platform dependency, not a theoretical objection.

The Intel Management Engine (ME), now commonly described as part of the Converged Security and Management Engine (CSME), is a privileged firmware subsystem separate from the host operating system. "Ring -3" is an informal security-community label, not an architectural CPU ring. Intel Active Management Technology (AMT) uses CSME on supported vPro systems to provide out-of-band management. ME is widespread; remote AMT networking is a separate capability that must be present and provisioned. The relevant properties are concrete:

  1. ME operates while the host processor is active. Configured AMT platforms can also remain manageable in supported sleep or soft-off states while connected to AC power. Intel's documentation states that AMT is not active in sleep or off states on battery power.

  2. Provisioned AMT uses the platform's wired or supported wireless adapter for out-of-band access. Depending on configuration, it can share the host address or use separate network settings; a distinct MAC and IP address are not universal properties of every ME installation.

  3. AMT implements a management channel independent of the host OS and supports functions such as remote power control, provisioning, firmware configuration, and, on supported systems, keyboard-video- mouse redirection.

  4. In out-of-band mode, provisioned AMT responds to management traffic, enabling diagnosis and remote access. On systems where an administrator has provisioned those features, the management plane operates below the host OS and remains reachable when the OS is unavailable.

    Intel has published serious CSME and AMT vulnerabilities, including the remotely exploitable AMT authentication flaw INTEL-SA-00075. These vulnerabilities affect the platform below Qubes and Xen; AEM's TXT requirement makes that firmware layer part of its measured-launch dependency. https://www.intel.com/content/www/us/en/support/articles/000024133/technologies.html

    • https://www.intel.com/content/www/us/en/docs/active-management-technology/developer-guide/2021/getting-started-with-intel-active-management.html
    • https://www.intel.com/content/www/us/en/support/articles/000102462/technologies.html
    • https://dl.dell.com/manuals/all-products/esuprt_laptop/esuprt_latitude_laptop/latitude-xt2_administrator%20guide_en-us.pdf

    AMD's Platform Security Processor is another privileged firmware subsystem, but I have not established that it has Intel ME's independent network-management path. Coreboot and Libreboot can replace or reduce parts of the vendor boot stack on supported hardware; they cannot generally remove firmware required inside the silicon. Their advantage over UEFI Secure Boot is inspectability and owner control, whereas Secure Boot verifies an authorized chain without making that chain auditable. https://libreboot.org/docs/linux/grub_hardening.html

    A vulnerability in Intel CSME or AMD PSP does not automatically expose VM data. Code execution in a sufficiently privileged firmware component can nevertheless bypass assumptions made by the hypervisor and operating system, so these subsystems belong in the platform threat model.

More on this topic from an authority in the field: https://inv.nadeko.net/watch?v=B4cOQOXjxew

A physical attacker can replace boot components, modify firmware, or instrument hardware below the operating system. TPM measurements can detect defined changes when the measurement chain and reference values remain trustworthy; they cannot prove that every firmware component is benign. Full-disk encryption, verified boot or filesystem policy, immutability, and kernel hardening address separate parts of that threat. Recovering a disk on another machine is safe only when the data remains encrypted and the original platform never obtained its keys.

Ordinary users cannot audit the complete TPM, Intel ME, or other proprietary firmware implementation before purchase. These components add privileged code, persistent state, and update mechanisms below the OS, so the trust claim must include them rather than treating the TPM as an independent proof of platform integrity.

Does Qubes use full disk encryption (FDE)?

By default, Qubes OS uses LUKS/dm-crypt to encrypt everything except the /boot partition.

Qubes therefore addresses physical attacks through a chain that still trusts privileged processor firmware, TPM behavior, Intel TXT, and the measured components. Encrypting /boot does not by itself solve pre-boot tampering because firmware must obtain or verify the code needed to unlock it. Linux systems, GrapheneOS, OpenBSD, and NetBSD use different combinations of verified boot, measured boot, encryption, owner-controlled keys, and physical custody. My criticism of Qubes is not that those systems eliminate platform trust; it is that AEM adds a complex, Intel-specific trust chain to an already complex platform.

9 - Weak fit for server workloads

Qubes OS is a poor fit for server use because it is explicitly a single-user desktop system. That scope does not invalidate its desktop isolation, but it prevents Qubes from replacing the server platforms I trust for unattended services, durable storage, remote administration, and fleet operations.

Server platforms prioritize stable service interfaces, remote administration, centralized logging, predictable updates, long support windows, and recovery procedures. OpenBSD, FreeBSD, RHEL, and other server-oriented systems build those properties into documented operational models. They can also run desktops, but desktop suitability is not a security test.

Availability, integrity, recoverability, and auditability are security properties for a server. Qubes does not claim to provide the high-availability, headless-management, or fleet-lifecycle features required for that role. I therefore reject recommendations that extend its desktop security claims to server workloads.

Qubes supports persistent qubes as well as disposables, so the operating system is not wholly disposable. Its management model still centers interactive desktop domains, template-root filesystems, and disposable work sessions rather than replicated services and durable storage. Destroying a compromised disposable limits persistence in that domain; it is containment after exposure, not a server recovery or continuity plan.

Making Qubes credible as a server platform would require redesigning its disposable-domain lifecycle, storage model, remote administration, hardware support, and availability guarantees. Incremental hardening cannot supply those missing operational properties.

10 - Networking exposure: trust in NetVMs and the split-driver model

Qubes centralizes network access in one or more network-facing qubes. A network domain such as sys-net owns the physical device and its driver; client qubes use a Xen virtual-network frontend, while a backend in the provider qube forwards their traffic. This moves physical network drivers out of dom0 but creates an explicit frontend/backend boundary.

The physical network domain is a primary external attack surface: it processes device input, wireless firmware interactions, link-layer traffic, and the Linux network stack. VPN and Tor software normally run in separate ProxyVMs, while browsers belong in AppVMs. Split drivers reduce driver code in dom0, but Xen frontends and backends still exchange guest-controlled data through grant tables and event channels. Those interfaces require the same scrutiny as every other privileged parser boundary.

Remote exploitation of NetVMs can lead to persistent compromise of network qubes and staged attempts at privileged escapes, data exfiltration, or manipulation of other qubes' network traffic. For attackers, a NetVM is an obvious target: it parses untrusted traffic and controls another qube's network path. Its compromise can expose or alter that traffic and create a staging point for attacks on privileged Xen interfaces.

Official support for a smaller hardened Linux network domain, or for a carefully integrated OpenBSD network domain, would give users a different network stack and policy surface. pfSense and OPNsense are designed as appliances, not drop-in Qubes NetVM templates. A physical router or firewall can move policy and some protocol handling off the laptop, but the local network domain still owns the client hardware. At that level of redesign, I would rather use a different operating system.

11 - Forensics, logging, and incident response limitations

Qubes' compartmentalization and disposable-qube model complicate centralized, tamper-evident logging and post-incident forensic analysis, reducing assurance after a suspected compromise.

Effective incident response relies on reliable logs, evidence custody, and the ability to reconstruct an attacker's actions. Qubes stores logs across separate domain filesystems, and logs created inside a disposable qube normally disappear with that qube. A compromised domain can also falsify its own application-level records before they leave the domain. These properties complicate host-wide correlation; they do not provide the amnesic-session guarantees for which Tails is designed.

This can leave users unable to tell whether their system has been compromised. Instead of reducing damage, the model can make the attacker harder to see and therefore more comfortable staying inside the environment.

After a breach, investigators may find incomplete telemetry, missing cross-qube event correlation, and lack of secure, centralized audit trails. That reduces the ability to determine scope, persistence, and exfiltration, and it complicates proving whether a host-level compromise occurred (hypervisor/dom0) versus a guest compromise. For high-assurance environments this weakens incident handling and forensic confidence. In the worst case, malware can remain active without the user's knowledge because the evidence needed to prove compromise was never preserved. That is not a small weakness.

Mitigations have limits. Best practice is to forward immutable, signed logs off-host to a remote collector under operator control (write-once storage or secure SIEM); use cryptographic attestation where possible; and maintain dedicated, high-trust audit qubes with strict ingestion policies. These measures add operational complexity and still require careful threat modeling to avoid introducing new attack channels. At that point, I would rather look for something simpler and stronger.

Security by Correctness

The assumption here is obvious: if we can produce software that doesn't have bugs (nor any maliciously behaving code), then we don't have security problems at all.

Security-focused software still requires design review, code audit, testing, and rapid correction. That applies to Xen, Linux, Fedora, Qubes services, and firmware.

The only problem is that we don't have any tools to make sure that a given code is correct (in terms of implementation, design and ethical behavior).

The same question is applied back to Qubes itself: design quality, implementation quality, and governance all still matter, even in a virtualization-based model.

But if we look at various efforts in computer science, we will notice a lot of effort has been made to achieve Security by Correctness: safe languages, code verifiers (although not sound ones, just heuristic based), developer's education, manual code audit, etc.

The same rule applies to Xen and every Qubes template. Virtualization does not eliminate the need for secure implementation or trained developers. Qubes uses Linux kernels in dom0 and its standard service qubes, so vulnerabilities in their reachable configurations remain relevant even when Xen contains some guest failures.

Microsoft's famous Secure Development Life-cycle is all about Security by Correctness.

The quotation refers to Microsoft's Security Development Lifecycle, not the Windows product-support lifecycle. SDL integrates security requirements, threat modeling, implementation rules, testing, release review, and incident response into software development. It is a valid example of systematic defect prevention, although Microsoft also uses exploit mitigations and isolation rather than relying on correctness alone. Microsoft's current SDL practices document that broader scope.

The only problem is: all those approaches sometimes work and sometimes do not, sometimes they miss some bug

This limit applies to every software-development method. Isolation contains selected failures, but the isolating software can also contain defects. A hypervisor boundary is therefore one control in a layered design, not an escape from implementation quality.

and also there are problems that I simple don't believe can be addressed by automatic code verifiers or even safe languages, like e.g. logic/design bugs or deciding on whether a given code behaves maliciously or not (after all this is an ethical problem in many cases, not a computer science problem).

Qubes OS should be evaluated like any other software project: by design quality, implementation quality, and operational outcomes, not by architectural claims alone. Its design choices should not be treated as if they transcend reality or sit above ordinary engineering limits. In the end, Qubes is still software designed by people.

No lower Qubes layer protects the system from a malicious or incorrectly implemented Xen binary with full hypervisor authority. Adding another virtualization layer would add complexity rather than establish Xen's correctness. Qubes addresses supply-chain risk through signed updates and controlled repositories, but those controls still trust release keys, build systems, and maintainers.

Source review alone cannot establish that a distributed binary corresponds to that source. Auditing the build system, using reproducible builds, comparing independently produced artifacts, and applying diverse double compilation address different parts of the "Trusting Trust" problem. The remaining trust belongs to a documented process and multiple verifiers, not to an architectural label or one developer's reputation.

See about this in Ken Thompson's famous document, Trusting Trust: https://www.cs.cmu.edu/~rdriley/487/papers/Thompson_1984_ReflectionsonTrustingTrust.pdf

Security by isolation

Simple as it sound, in practice the isolation approach turned out to be very tricky to implement.

Virtualization does not remove that policy problem. Qubes still has to define domains, qrexec permissions, device ownership, storage boundaries, and trusted administrative paths.

One problem is how to partition the system into meaningful pieces and how to set permissions for each piece. The other problem is implementation - e.g. if we take a contemporary consumer OS, like Vista, Linux or Mac OSX, all of them have monolithic kernels, meaning that a simple bug in any of the kernel components (think: hundreds of 3rd party drivers running there), allows to bypass of the isolation mechanisms provided by the kernel to the rest of the system (process separation, ACLs, etc).

The statement is incomplete. Kernel-level and user-space mechanisms limit the authority exposed to applications and the impact of bugs. Properly partitioning and defining those policies remains difficult. Monolithic kernels retain privileged drivers and subsystems, while LSMs, seccomp, page-table isolation, hardware access controls, and driver isolation narrow specific paths to system-wide compromise.

A mainline Linux CVE does not automatically affect every Ubuntu, openSUSE, or Fedora installation. Exploitability depends on the shipped configuration, reachable subsystem, privileges, hardware, and active mitigations. Randomization and related exploit mitigations do not remove the underlying bug; they obstruct reliable exploitation and reduce the set of usable primitives.

A microkernel can reduce privileged code and isolate services, but those properties do not establish implementation quality. A monolithic kernel can compensate with smaller scope, auditing, privilege separation above the kernel, and exploit mitigations. Virtualization contains some failures; it does not correct insecure code underneath the boundary.

Many kernel exploits in real attacks provide post-compromise privilege escalation, but remotely reachable kernel interfaces and malicious devices can also make the kernel the initial target. The relevant question is which interfaces are exposed and which mitigations constrain the exploit.

Obviously the problem is because the kernels are monolithic. Why not implement Security by Isolation on a kernel level then? Well, I would personally love that approach, but the industry simply took another course and decided that monolithic kernels are better than micro-kernels, because it's easier to write the code for them and (arguably) they offer better performance.

The argument omits kernel-hardening and isolation primitives beyond VMs: Namespaces, Capabilities, RCTL, Jails, Zones, Capsicum, Seatbelt, SELinux, AppArmor, vnet, devfs, VFS, Chroot, Smack, Seccomp, LSM hooks, Landlock, SMEP, SMAP, retpoline, NX, DEP, Kernel Page-Table Isolation (KPTI), and eBPF/XDP. These mechanisms have different limits, but their existence disproves the claim that VM boundaries are the only available form of software isolation.

If the monolithic kernel is the root problem, Qubes does not remove it. dom0, service qubes, and the common templates still use Linux kernels. Xen places boundaries between those kernels, but it does not turn them into seL4, L4, Hurd, or Minix, nor does it eliminate their exposed interfaces inside each domain.

A microkernel design can reduce privileged code, but Qubes' actual architecture must be judged as shipped. Xen, dom0, device domains, qrexec, and guest kernels divide responsibility across several trust boundaries. That can contain a guest compromise while leaving failures in the privileged control path capable of crossing domains.

Many believe, including myself, that this landscape can be changed by the virtualization technology.

The claim again treats virtualization itself as the result rather than identifying the authority retained by each component.

Thin bare-metal hypervisor, like e.g. Xen, can act like a micro kernel and enforce isolation between other components in the system - e.g. we can move drivers into a separate domain and isolate them from the rest of the system.

A hypervisor is not required to isolate every service: kernels can also use processes, capabilities, sandboxes, jails, namespaces, and driver domains. The hypervisor itself remains a privileged boundary. Xen compromise can invalidate every guest boundary, whereas compromise of an unprivileged service on bare metal does not by itself imply kernel compromise.

Xen does not repair vulnerabilities inside a guest or its applications. It can contain their effects at the domain boundary, and that is a genuine security benefit. The cost is additional privileged code, cross-domain interfaces, and a shared failure point. Treating the containment benefit as proof of whole-system superiority ignores that cost.

Also, how to make sure that the hypervisor itself is not buggy?

This is the key point of the section: hypervisor trust is a critical assumption. Xen's assurance comes from its architecture, implementation, review, mitigations, testing, and update process, not from the word "hypervisor."

Xen contains substantial C and assembly code and is not a formally verified hypervisor. Its privilege makes memory-corruption bugs consequential. Isolation protects Xen from ordinary guest authority only to the extent that Xen correctly validates hypercalls, grant mappings, emulated devices, interrupts, and other guest-controlled inputs. The relative rarity of commodity hypervisor malware reduces routine exposure; it is not a security guarantee.

Security by Obscurity (or Security by Randomization)

Finally we have the Security by Obscurity approach that is based on the assumption that we cannot get rid of all the bugs (like in Security by Isolation approach), but at least we can make exploitation of those bugs very hard. So, it's all about making our system unfriendly to the attacker.

The label "obscurity" conflates two different ideas. ASLR and other randomized mitigations deliberately withhold per-execution state even when their design is public. Relying on an uncommon platform to escape attacker attention is obscurity in the ordinary sense. Desktop hypervisors receive less commodity-malware attention, but targeted Xen exploits do not depend on that ecosystem being common.

Randomization and exploit mitigations can raise attacker cost in ways that complement virtualization. They are not replaced by virtualization at all.

The obvious disadvantage of this approach is that it doesn't prevent the bugs from being exploited - it only make the meaningful exploitation very hard or even impossible.

Making exploitation significantly harder is a practical security benefit. A mitigation need not eliminate the bug to block a working exploit or force an attacker to obtain additional primitives.

But if one is concerned also about e.g. DoS attacks, then Security by Obscurity will not prevent them in most cases.

DoS belongs in a desktop threat model, but it is not equivalent to confidentiality or integrity compromise. A local process can exhaust memory, CPU, storage, or privileged service capacity; remote attacks can deny access to the network or an upstream service. Qubes must control local inter-domain resources, while providers and network operators must handle attacks beyond the endpoint.

Protection against DoS is done with hardware isolation, router filters, load balancers, scrubbing farms at the network edge, CDN/Anycast, BGP ACLs, rate-limiting, and related controls. This is core server infrastructure, which is why desktop-centric virtualization models are not enough by themselves.

Randomization blocks some exploitation paths but does not control resource exhaustion by itself. Correct resource accounting, rate-limiting, quotas, scheduling, and bounded parsers address local denial of service. Network-layer DDoS requires capacity and filtering upstream of the endpoint.

Virtualization can enforce per-domain CPU and memory limits and make a failed service easier to restart. It cannot guarantee quick recovery or absorb traffic that has already saturated the external link.

The other problem with obfuscating the code is the performance (compiler cannot optimize the code for speed) and maintenance (if we got a crash dump on an obfuscated Windows box, we couldn't count on help from the technical support).

Security controls impose specific usability and maintenance costs; the tradeoff is not a universal one-for-one law. Removing a feature removes its code paths, while careful tooling can preserve operations around defensive changes. OpenBSD proves the latter point: library-order randomization, KARL, and randomized relinking of daemons such as httpd and smtpd coexist with symbol handling and crash analysis designed for those layouts.

Strong controls impose costs in compatibility, performance, maintenance, or hardware support. The critique is incomplete when it rejects randomization for operational cost while accepting a larger virtualization stack to preserve application compatibility.

Microkernels and hypervisors incur different IPC, scheduling, and device-management costs. Invoking performance without quantifying those costs cannot justify one architecture while dismissing mitigations in another.

Finally there is a problem of proving that the whole scheme is correct and that our obfuscator (or e.g. ASLR engine) doesn't introduce bugs to the generated code and that we will not get random crashes later (that we would be most likely unable to debug, as the code will be obfuscated).

Randomized code remains debuggable when builds preserve symbols and layout metadata. Test suites can validate invariants, and crash tooling can map an observed randomized layout back to the corresponding symbols. Randomization changes the debugging workflow; it does not inherently prevent debugging or auditing.

Every method creates a channel and requires scanning, format constraints, or one-way policy appropriate to the threat. Qubes' inter-VM copy mechanism makes that channel explicit and mediated, but it still moves attacker-controlled data onto the same machine.

The real tradeoff is consolidation. Qubes makes cross-domain transfer easier to govern than ad hoc copying, while physical separation removes the common hypervisor and hardware at greater cost and inconvenience.

Physically separate computers running conventional OSes are still independently vulnerable to most conventional attacks due to their monolithic nature.

Qubes also runs monolithic guest kernels. The distinction is that a guest-kernel compromise should stop at the domain boundary; the quoted statement does not explain why the same kernel becomes harmless merely because Xen surrounds it.

Qubes combines conventional Fedora or Debian templates, Linux kernels, GNU userland, and optional Windows guests with a distinctive Xen management and GUI layer. Its novelty is the orchestration of those domains, not replacement of their kernels or libraries. The resulting system must therefore secure both the conventional components and the Qubes-specific control plane.

Hardware separation prevents one machine's kernel or hypervisor flaw from directly crossing into another machine. Each system still requires secure transfer policy, updates, firmware, and physical protection.

The comparison with physical separation fails on boundary strength. Qubes shares one CPU, firmware stack, memory subsystem, and hypervisor; separate machines do not. Qubes can be cheaper and easier to operate, but those operational benefits do not make its shared boundary stronger than independent hardware.

Malware which can bridge air gaps has existed for several years now and is becoming increasingly common.

Air-gap crossing requires a channel. Removable media, compromised peripherals, supply-chain implants, radio hardware, acoustic or optical emissions, and an operator moving data can provide one. Qubes can restrict software paths on its own machine, but it does not create an independent hardware boundary or eliminate covert physical channels.

Research examples include AirHopper, GSMem, and USBee, which encode data in electromagnetic emissions or cable signals; Fansmitter, BitWhisper, and DiskFiltration, which use fan speed, heat, vibration, or acoustic output; LED and infrared channels; and MAGNETO or ODINI, which use magnetic fields. Each technique has specific transmitter, receiver, distance, and bandwidth requirements.

Defending against those channels requires controls matched to the medium, including device exclusion, shielding, separation distance, emission controls, and operational procedure. Qubes provides no general defense against a physical channel below or outside Xen.

Published covert-channel demonstrations usually depend on controlled receiver distance, calibrated sensors, and low environmental noise. Those constraints limit range and throughput in real deployments; they do not make every field attack impossible. An example is the attack discovered in 2024 in which hackers use the friction sound caused by the finger on the cell phone screen to steal fingerprints. https://www.ndss-symposium.org/wp-content/uploads/2024-618-paper.pdf

This research used a controlled environment, specific sound capture, and noise handling. The reported setup achieved 27.9% partial and 9.3% full fingerprint inference under its stated evaluation conditions. Greater distance, uncontrolled microphones, movement, and environmental noise reduce those rates further. The paper demonstrates a channel; it does not demonstrate reliable collection in an arbitrary field environment.

Citing an air-gap covert channel without its distance, bandwidth, receiver, and environmental assumptions obscures the actual threat. A Qubes security claim must identify which component blocks the channel and under what conditions. Without that mechanism, invoking exotic research does not establish that Qubes protects the user.

What is the main concept behind Qubes?

To build security on the Security by Compartmentalization (or Isolation) principle.

Compartmentalization is only as strong as the components that enforce it. Qubes does not formally prove Xen and its complete control plane, so its assurance depends on implementation quality, review, mitigations, testing, and timely correction of vulnerabilities.

What about safe languages and formally verified microkernels?

In short: these are non-realistic solutions today. We discuss this in further depth in our Architecture Specification document.

Xen is largely implemented in C with architecture-specific assembly and is not formally verified as a complete hypervisor. That does not make every memory-management exploit possible, but it leaves memory-corruption classes that safe-language and verified-kernel proposals are intended to remove. Dismissing those proposals as impractical does not answer the assurance gap in Xen.

Why does Qubes use virtualization?

We believe that this is currently the only practically viable approach to implementing strong isolation while simultaneously providing compatibility with existing applications and drivers.

The statement identifies a design judgment, not a demonstrated law. Qubes supports it with compatibility and deployment experience, while the hardware limitations documented earlier constrain the breadth of that compatibility. The project should state the alternatives and the measured cost of rejecting them.

The unfortunate reality right now is that an operating system cannot be secure without a certain minimum number of proprietary closed-source blobs (e.g., CPU microcode updates). A 100% free operating system that excludes all such blobs is vulnerable to known exploits and is therefore unsuitable for any use case where security matters.

CPU microcode updates correct known processor defects; they do not guarantee the security of the processor or platform. Intel CSME, AMD PSP, TPM firmware, and device firmware remain non-auditable privileged dependencies with their own vulnerability and update histories.

OpenBSD does not place proprietary firmware in its base system. Its fw_update(8) path installs separately distributed firmware needed by detected hardware, leaving that dependency explicit. OpenBSD also derives its primary security model from kernel and userland design, not from processor virtualization.

My criticism is not directed at installing vendor fixes. It is directed at making VT-x or AMD-V, VT-d or AMD-Vi, microcode, firmware tables, and the IOMMU indispensable enforcement layers. Qubes gains VM isolation from that hardware and simultaneously inherits its defects; both sides of the trade-off belong in the security claim.

A core tenet of the Qubes philosophy is distrust the infrastructure, where the infrastructure refers to things like hosting providers, CDNs, DNS services, package repositories, email servers, PGP keyservers, etc.

Qubes integrates Xen, Linux, Fedora or Debian templates, Tor/Whonix, CPU virtualization, proprietary firmware, and TPM measurements. The project writes substantial management, GUI, and qrexec code, but it does not control the foundational hypervisor, kernel, or firmware. Its "distrust the infrastructure" principle therefore means containment of selected third-party components, not independence from them.

As a project, we focus on securing endpoints instead of attempting to secure the middle (i.e., the infrastructure)

Endpoint cryptography can preserve confidentiality and authenticity across an untrusted network, so securing the endpoint is a coherent goal. It does not preserve availability or hide all metadata, and a compromised endpoint still defeats the model. Qubes must therefore explain which infrastructure failures its endpoint boundary contains instead of treating the middle as irrelevant.

since one of our primary goals is to free users from being forced to entrust their security to unknown third parties.

The stated goal conflicts with the dependency graph that follows.

Xen, Fedora + ecosystem (Xorg, systemd, rpm, dnf), Debian + ecosystem, GNU software, Linux + vendor blobs, libvirt, CPU microcode from Intel/AMD, device firmware, hardware features and vendor implementations (VT-x/AMD-V, VT-d/AMD-Vi, SLAT/EPT/RVI, TPM, DMAR/ACPI tables, etc.)

Instead, our aim is for users to be required to trust as few entities as possible (ideally, only themselves and any known persons whom they voluntarily decide to trust).

In practice, users must also trust the maintainers and delivery paths of every privileged third-party component listed above.

We believe that many attempts to make the infrastructure appear trustworthy actually provide only the illusion of security and are ultimately a disservice to real users.

Yes, I agree. I say the same.

Qubes correctly rejects blind trust in hosting and distribution infrastructure. The same standard must apply to Xen, dom0, template repositories, build systems, and signing keys: each needs a defined verification or containment boundary.

Although we caution users against placing undue trust in this website because we distrust the infrastructure, we have no objection to enabling website security features when doing so is relatively costless and provides some marginal benefit to website visitors.

Enabling inexpensive browser defenses does not contradict distrust; it is ordinary defense in depth. My narrower objection is that the site still ships client-side JavaScript, adding browser-side code where a mostly static documentation site could expose less.

Each qube has read-only access to the template on which it's based, so if a qube is compromised, it cannot infect its template or any of the other qubes based on that template.

The statement is accurate for Qubes' normal storage path: an AppVM receives a read-only template root and writes to its own private overlay, so an ordinary AppVM compromise does not modify the offline TemplateVM or sibling AppVMs. The guarantee has precise boundaries. A TemplateVM can also be compromised through its own update or software-installation path. Such a compromise affects every dependent AppVM after restart. 16 - Limits against zero-day attacks

A zero-day (also known as a 0-day) is a vulnerability or security hole in a computer system unknown to its developers or anyone capable of mitigating it. Until the vulnerability is remedied, threat actors can exploit it in a zero-day exploit, or zero-day attack.

https://en.wikipedia.org/wiki/Zero-day_vulnerability

Qubes' defense against zero-days depends on the boundary the bug crosses. A compromise in a guest application or guest kernel can remain confined to that qube. A flaw in Xen or in code that Qubes treats as security-critical can invalidate separation across domains. The useful measure is not all code installed in every VM; it is the code reachable across a trust boundary and the authority that code holds.

Qubes makes Xen-enforced compartmentalization its primary control. Its own security-critical code inventory includes Xen, xenstore and block backends, dom0-side qrexec, GUI and audio components, the memory manager, and selected RPC services. Compromising one ordinary app qube does not automatically compromise those components, which is the architecture's central security benefit.

First, guest kernels deliberately interact with Xen through hypercalls, event channels, grant tables, and virtual devices. Those interfaces enforce isolation, but they are also the guest-facing attack surface of the privileged layer. A vulnerability that gives a guest code execution in Xen crosses every isolation boundary enforced by that Xen instance. Device assignment creates a separate hardware boundary: the IOMMU restricts DMA, while a flaw or misconfiguration in the IOMMU, firmware, or platform can defeat that restriction.

The boot chain loads Xen and the administrative domain, dom0. Dom0 manages the other domains and intentionally has no network interface, which removes a major remote attack path. App qubes still run complete guest kernels and userlands, but that code is not automatically part of the TCB for other qubes. Only the interfaces and privileged services that process guest-controlled input belong in that cross-domain analysis.

Second, system-wide compromise has more than one path. Relevant targets include Xen, guest-facing dom0 services, the GUI path, qrexec and its policy engine, storage backends, and privileged update processing. Network and USB domains reduce the authority of exposed driver stacks; they do not remove the possibility of a second exploit against Xen or another trusted component. File copy, clipboard, and RPC services deliberately cross domain boundaries, so their parsers and policies require the same scrutiny.

Third, Qubes does not replace exploit mitigations. It inherits mitigations from Xen, Linux, Fedora, Debian, and the applications running inside each qube. ASLR, W^X/NX, KPTI, retpolines, and kernel hardening raise exploit cost within their respective layers; compartmentalization limits authority after a successful compromise. Neither control makes the other unnecessary.

GrapheneOS, OpenBSD, and hardened Linux distributions defend different boundaries. OpenBSD emphasizes an integrated, audited base system and exploit mitigations; GrapheneOS hardens Android application and kernel boundaries; Secureblue applies a hardened policy to Fedora. Qubes instead prioritizes separation between desktop domains. Comparing them requires a threat model, because reducing code in one trusted layer and adding an isolation boundary solve different problems.

Zero-day risk differs by boundary. A guest-application zero-day can remain confined to one qube; a zero-day in Xen, dom0, a device domain, qrexec, firmware, or the update path can cross or bypass that boundary. Qubes depends on several third-party projects for disclosure and patch timing. Systems such as OpenBSD reduce this exposure differently: they audit a smaller integrated base and apply mitigations that raise exploit cost before a specific bug is known.

Qubes makes compartmentalization its primary control. That is effective when the unknown bug remains inside a guest boundary; it does not fix, randomize, or contain a bug in the shared privileged layer. A smaller privileged TCB, proactive auditing, and exploit mitigations provide structural resistance at the layer where a Qubes-wide zero-day would execute.

Qubes officially supports Fedora and Debian templates. Whonix templates are supported by the Whonix Project; other community templates have separate maintainers, and the Qubes OS Project neither tests them nor supplies their updates. Windows qubes can be installed, but Qubes cannot distribute a preconfigured Windows template. OpenBSD is therefore not an officially supported Qubes template.

In all cases, the Qubes OS Project does not provide updates for these templates.

In addition, these templates may be somewhat less stable, since the Qubes developers do not test them.

https://doc.qubes-os.org/en/latest/user/templates/templates.html

Community templates add another maintainer and update channel to the user's trust model. That does not weaken Xen's isolation by itself, but it does change who is responsible for vulnerabilities inside the guest and how quickly fixes arrive.

Installing another guest operating system increases code inside that guest, not necessarily the TCB for every other qube. The cross-domain risk comes from the additional hypercalls, virtual devices, qrexec services, and user-authorized transfers exposed to guest-controlled input. The protection against a malicious guest is Xen plus the narrow set of privileged services that communicate with it.

A smaller hypervisor or microkernel could reduce privileged code, but replacing Xen with seL4, an L4 system, MINIX 3, or GNU Mach is not a component swap. Qubes would need new virtualization, device-isolation, management, GUI, and RPC implementations with equivalent hardware and guest support. That redesign would require its own security analysis; the microkernel label alone would prove nothing.

Conclusion

I do not consider Qubes OS the strongest general-purpose security platform. It is a specialized desktop system for users whose threat model benefits from separating work, personal, network, and disposable activities into VM-backed domains. That benefit must justify its hardware constraints, privileged virtualization stack, and operational complexity.

Some criticisms in this article also apply to many other systems, but my claim is that Qubes OS combines all of these concerns at once. The following section presents stronger alternatives for security and isolation.

For a disposable anonymity session, Tails and a Kicksecure live system have a narrower operational scope; Whonix provides a dedicated gateway/workstation split. Whonix can also run on KVM, but neither KVM nor Xen is categorically safer without comparing the host, device model, management stack, and patch state.

Qubes OS's compartmentalization limits data flow and persistence across desktop domains, but its guarantees terminate at shared privileged infrastructure. Xen, dom0, and the Qubes security-critical services form the TCB. Paravirtualized and emulated interfaces expose deliberate guest-to-hypervisor channels, while device assignment depends on the platform IOMMU and firmware. Disposable qubes limit persistence inside a guest but do not remove those privileged paths. Qubes' desktop-centric design is therefore a poor fit for a high-assurance server that requires a minimal auditable TCB, long support windows, and headless management.

I reject any design argument that treats isolation as a substitute for correct code, bug fixes, and exploit mitigations. Qubes must earn trust through the behavior of Xen, dom0, service qubes, qrexec, and its update process, not through confidence in compartmentalization alone.

Qubes is effective when the threat is a malicious document, website, or application whose access should stop at one desktop domain. Its assurance is weaker when the adversary can target Xen, dom0, firmware, certified hardware, or the update chain. Users should choose it for the first boundary, not assume that it solves the second.

The practical tradeoff is explicit desktop-domain separation in exchange for hardware constraints and operational complexity. Qubes does not replace a small trusted computing base, secure code, or an independent physical boundary.

Points to consider

VMs provide operating-system compartmentalization and make domains convenient to manage. Process sandboxing can enforce a narrower policy with less machinery, but an escape reaches the sandboxing process's user context and may become the first step in a privilege-escalation chain. The two boundaries defend different scopes.

Qubes' isolation terminates at Xen, dom0, and shared hardware. A design with a smaller privileged boundary, or physical separation, provides stronger assurance against failures at that layer.

A VM boundary is privileged software, not an absolute wall. OpenBSD vmm is the hypervisor I prefer because its narrower feature set, userland device model, and process compartmentalization leave less host code and authority exposed to a guest.

https://www.openbsd.org/faq/faq16.html

OpenBSD added vmm after years of public skepticism from Theo de Raadt about hypervisor security. The current OpenBSD FAQ documents a narrow feature set and explicitly lists the following unsupported features; it does not claim that every omission was made exclusively for security:

  • Graphics
  • Snapshots
  • Guest SMP support
  • Hardware passthrough
  • Live migration across hosts
  • Live hardware change

KVM, Hyper-V, bhyve, and VMware support different guests, devices, and management workflows. Their broader feature sets may be necessary, but the architecture and patch history must be evaluated separately; feature count does not establish a security ranking.

It supports live migration, high-availability clustering (Corosync + Ceph), software-defined networking, professional backup via Proxmox Backup Server (incremental, encrypted, deduplicated), multi-factor authentication, and role-based access control. Qubes does not target these cluster and datacenter workflows.

Proxmox publishes free and enterprise subscription repositories and sells commercial support. It runs on broad server hardware and does not require Qubes-certified laptops. The management API, web interface, storage stack, clustering, QEMU, KVM, LXC, and optional Ceph services create a substantial server attack surface, so no evidence supports calling it dramatically smaller than Qubes.

For users who need virtualization-based server isolation, commercial support, high availability, and managed backups, Proxmox VE solves the correct problem. It is not a drop-in Qubes desktop replacement, and its security still depends on host hardening, network policy, prompt updates, and minimizing exposed management services.

  • GrapheneOS is a privacy- and security-focused mobile OS with Android app compatibility, developed as a nonprofit open-source project. It is my strongest mobile recommendation and supports only selected Google Pixel devices. https://grapheneos.org Android user profiles separate application instances and profile data, while verified boot, hardware-backed key storage, exploit mitigations, and a hardened app sandbox protect the common platform. This is a simpler mobile isolation model than Qubes, not a replacement for desktop VMs or physical separation.

  • NixOS provides a declarative system model, reproducible package builds, atomic generation changes, and rollbacks. Configurations can span many Nix modules rather than one file, and declarative state does not make the chosen services secure. I still object to its dependence on systemd, but its package and deployment model is technically excellent. https://nixos.org SixOS is an experimental effort to build a Nix system without systemd:

    • https://inv.nadeko.net/watch?v=gSW3YJ8uyBI
    • https://codeberg.org/amjoseph/sixos

    SixOS is still under development, and I have not installed or audited it. I therefore cannot rank it against Secureblue. A hardened NixOS could exceed Secureblue only if its evaluated policy actually supplied stronger kernel, service, sandbox, and update controls; declarative configuration alone does not establish that result.

For compatible Linux systems, also evaluate LKRG (Linux Kernel Runtime Guard) and hardened_malloc. LKRG is an out-of-tree kernel module with kernel-version and maintenance costs; hardened_malloc changes allocator behavior and can expose application compatibility problems. Deploy either only after testing it against the actual kernel and workload.
