Security

From a strict security perspective, Qubes OS is not reliable

Written by FlyWithMe (a SimpleX chat user) - Updated September 3, 2026

The aim of this article is to provide constructive but uncompromising criticism of Qubes OS, or "XenOS" as I sometimes call it. I will expose its security weaknesses, acknowledge its strengths, suggest possible improvements, and recommend alternatives that I consider more robust and reliable for different kinds of users.

1 - Xen hypervisor

Qubes OS runs its domains on Xen, a type-1 hypervisor. Xen enforces memory and CPU isolation, but it is also a central point of trust: code execution in Xen can invalidate every domain boundary enforced by that Xen instance. Virtualization does not automatically provide stronger security than direct execution on hardened bare metal. Firmware, microcode, IOMMU, and speculative-execution flaws sit below the same boundary and can also weaken isolation.

With Intel VT-x, Xen executes in VMX root mode while guest kernels run in VMX non-root mode; AMD-V provides corresponding host and guest modes. The informal "ring -1" label describes Xen's position outside a guest's Ring 0, not a formally defined CPU ring. Xen's real authority comes from controlling second-stage memory translation, interrupts, virtual CPUs, and the interfaces presented to guests. If Xen is compromised, the scope of the attack can therefore be catastrophic.

Current Qubes documentation states that releases use PVH by default for qubes without assigned PCI devices and HVM for qubes that require PCI assignment. PVH combines hardware-assisted CPU and memory virtualization with paravirtualized I/O; HVM presents a fuller hardware model. Windows is not the only Qubes workload that receives hardware-assisted virtualization. Claims that nearly every non-Windows template uses legacy PV are obsolete.

The actual virtualization modes do not rescue the design. Both PVH and HVM expose guest-controlled input to Xen and backend components. Paravirtualized I/O uses hypercalls, grant tables, event channels, and frontend/backend interfaces. Full virtualization adds device emulation that also parses hostile guest state. These dependencies increase complexity, attack surface, and opportunities for misconfiguration. This is the price of choosing convenience and performance over a smaller security boundary.

Full virtualization lets an unmodified guest run against emulated hardware, but it does not make the VM absolutely isolated: the hypervisor and device model remain privileged parsers. Implementations include KVM, Hyper-V, VirtualBox, and OpenBSD vmm. My criticism is not the obsolete claim that HVM alone is safe; it is that Qubes builds its security promise on a large virtualization stack whose shared failure points remain beneath every qube.

Several attacks on Qubes OS originate in an AppVM, and some historical exploits have used Xen vulnerabilities to escape the guest and compromise Dom0 or other VMs. However, not all attacks go through Xen; there are also vectors via firmware (ME/PSP), drivers, IOMMU, or flaws in Dom0 and SystemVMs. The most important link in the system is also the most vulnerable, so vulnerable that support for using OpenBSD for dom0 and domU has been officially proposed and debated in Qubes issue 4551, with broad agreement that it would be very good and extremely beneficial for the security of Qubes OS. However, this does not happen because substantial Qubes integration would have to be ported.

The use of OpenBSD for NetVM (sys-net) was also proposed, due to its extreme vulnerability to attacks. The proposal also records the substantial integration and hardware-support work.

Update: A community guide shows that it is possible to use OpenBSD as sys-net, although I'm not sure it would be fully compatible as a NetVM. The guide is outdated and it isn't officially supported by the Qubes OS team.

But all this would only remedy the inevitable: the hypervisor will always be the weakest link. An OpenBSD running directly on the hardware tends to have a smaller attack surface than when running on a VM, because virtualization adds layers (hypervisor, firmware, drivers, devices) that broaden the risk surface. Many believe that the fact that dom0 does not connect to the internet makes it 100% secure, which is not true.

An exploited NetVM can, for example, serve as a starting point for attacks that escape to other VMs or to dom0, compromising the entire system. The fact that dom0 does not have internet access is good for protecting against remote attacks targeting dom0, which attempt to "bypass" the need to escape from a VM to access it; this simply does not protect against the escape of one or more compromised VMs. Logical isolation loses effectiveness if all VMs and services depend on the same underlying platform (in this case, Xen). The comparisons I reviewed showed fewer published CVEs and guest escapes for Hyper-V than for Xen in recent years, although raw totals across projects are not equivalent measurements. I still judge the Windows virtualization security model, especially on supported enterprise hardware, to be more mature than the Qubes OS model.

The argument I see most often from Qubes OS developers is denial, the first stage of trauma: "A hypervisor escape is rare," "these attacks are difficult to carry out," or "you have no reason to worry about it." That misses the point entirely. Xen has accumulated hundreds of Xen Security Advisories, many of them critical, including guest-to-host escapes. Hypervisors also benefit from security by obscurity because most commodity malware does not expect to run inside a VM and therefore does not bother attacking the hypervisor.

If this model becomes more popular (and it is), attackers will have more reason to target hypervisors, especially Xen. Qubes OS also does little to hide the fact that a guest is virtualized, which makes this problem easier to recognize from inside a VM. That brings us to the next issue.

2 - Lack of VM spoofing

In most VM setups, guest systems can easily detect that they are virtualized. On Windows, this can be visible through registry keys, drivers, processes, and other system artifacts.

An example of this fact is that when using both Windows and Tails (Linux) in a virtual machine, you will receive a notification from the guest OS indicating that the system is being virtualized.

This is why Tails warns you when it is running inside a virtual machine

Tails documentation: virtualization

This can be masked. There are many scripts and tutorials that try to hide virtual machine presence from the guest, and on Linux this can be easier because the user has more control over the environment:

  • NoVM (GitHub)
  • CloakBox (GitHub)
  • Making a VM undetectable to guest applications (VirtualBox forums)
  • VMwareCloak (GitHub)

Qubes OS does not try to do this kind of concealment, so malware can detect the VM context early and adapt its behavior, or an attacker with remote access may, upon realizing that they are in a virtualized environment, seek to exploit the hypervisor.

Because Qubes templates are already modified operating-system images, implementing spoofing should not be an absurd idea. The developers should define and test a supported anti-fingerprinting profile instead of leaving each template to disclose the virtualized environment independently.

3 - Linux-based attack surface

Qubes OS uses a Fedora-derived dom0 and standard Linux kernels. Qubes controls the dom0 package set and supplies security-critical updates independently of Fedora's ordinary lifecycle, so calling dom0 simply an unmaintained Fedora release would be inaccurate. The real problem is that its most privileged control plane still inherits a large Linux and Fedora codebase, plus Qubes-specific services, without the complete hardening policy of systems such as Secureblue. Those privileged Qubes-specific services also require their own review and update path.

A compromised sys-net cannot automatically read other qubes' memory; Xen and the IOMMU are specifically meant to prevent it. But memory corruption in Xen, a backend, or an IOMMU-facing path can defeat that boundary. Dismissing buffer overflows and memory attacks as rare is cowardly: large C and C++ codebases repeatedly report roughly two-thirds of their security bugs in memory-safety classes.

See my other article proving this: The C language and its biggest problem: evidence of its insecurity.

Attackers target the weakest link. Compartmentalization helps only when the privileged components underneath it are robust and patched quickly. It is "rare" until the system becomes popular enough to attract serious adversaries. Qubes' safety depends far too much on this kind of obscurity.

Qubes OS could improve this with kernel security patches such as Grsecurity/PaX and/or Linux-hardened support, LKRG, and compilation with hardening flags such as FORTIFY, PIE, and RELRO. It should also lean harder on Mandatory Access Control, such as TOMOYO or SELinux. Fedora templates support SELinux on Qubes OS, but the setup is outdated, the default policies are weak, and enforcing mode is not practical without breaking the system. Kernel self-protection, fewer privileged executables, disabled services, restricted namespaces, and enforceable MAC policy all belong in the baseline.

Fedora Secureblue is a good example of the bare minimum for a "reasonably secure operating system": kernel patches, hardened system defaults, and a strong MAC model with limited namespaces. Qubes OS does not do this by default.

4 - Operational complexity

Qubes OS is operationally complex, even for advanced users. The user must manage templates, disposable templates, domain labels, qrexec policy, update paths, device assignment, network chains, and storage semantics. Each relationship adds state that can be misunderstood or configured inconsistently. More complexity means more chances for human error, and human error can weaken both security and anonymity. This contrasts with Secureblue, GrapheneOS, and OpenBSD, which protect users against many mistakes by default and out of the box.

Qubes OS is not secure by default, and its current architecture cannot get there.

In short, more moving parts usually mean more opportunities for mistakes and misconfiguration. Complexity = Attack Surface, always.

5 - Systemd attack surface

Systemd is a demonic piece of junk. Run systemd-analyze security and see what it reports. My challenge is to bring every service to at least "OK" without completely breaking the system. The score covers selected unit properties rather than the security of an entire service, but it still exposes how little hardening many units receive. Qubes templates do not inherit every systemd hardening choice made by Secureblue.

Systemd centralizes many responsibilities. That concentration increases attack surface and raises the impact of failures. Systemd is currently divided into four layers:

  1. systemd Libraries (the base)
  2. systemd Core
  3. systemd daemons and systemd targets
  4. systemd Utilities

Each layer has programs and modules that parse configuration, messages, credentials, or service state, adding even more attack surface. It's almost like a complete operating system; in fact, a kernel plus systemd is already a complete operating system.

6 - Hardware support and compatibility problems

Qubes OS hardware compatibility is narrow in practice. Effective device isolation requires working IOMMU support, current Qubes releases require SLAT, and Xen, Linux, firmware, and individual devices must all work together. Anti Evil Maid (AEM) narrows the compatible set further because its design requires TPM 1.2 and Intel TXT. Getting all of that to work reliably on current software is real Russian roulette.

Outside the small certified-hardware list, users must consult the community hardware compatibility list (HCL) and test the exact machine, firmware revision, and Qubes release. The HCL records user reports, including reports for old Qubes versions; an entry is evidence about a specific configuration, not a current certification. When I collected the hardware data for this article, the certified list contained only 11 devices, and three of them no longer received CPU microcode updates.

Qubes OS certified hardware list

Outside that list, every security-relevant requirement must be verified on the exact configuration: IOMMU, SLAT, virtualization, device assignment, suspend behavior, firmware updates, and current CPU microcode. Missing microcode support leaves processor vulnerabilities without the vendor mitigations on which Qubes and Xen depend.

Pay attention to what the developers themselves say on the official website:

There is a class of security vulnerabilities that can be fixed only by microcode updates. If your computer or the CPU in it no longer receives microcode updates (e.g., because it is too old), it may not be possible for some of these vulnerabilities to be mitigated on your system, leaving you vulnerable.

This matters because Qubes OS depends heavily on CPU virtualization features such as Intel VT-x, Intel VT-d, AMD-V, and AMD-Vi. Its security depends on vendor microcode that supports those features, so vulnerabilities in that hardware or microcode affect Qubes directly. That dependency is ugly: the OS needs proprietary CPU code both to function/exist and to claim security.

In that sense, the security of Qubes OS depends less on Qubes itself and more on Intel and AMD engineering. This increases attack surface for both the OS and Xen instead of reducing it, and that dependency cannot be wished away.

One major and serious problem that almost no one seems to realize is that concentrating Qubes users on a tiny set of selected devices makes coordinated hardware and supply-chain attacks easier to focus. If an attacker knows that a target population buys particular devices from particular vendors, poisoning that supply chain becomes easier. This is not a fantasy: Operation Trojan Shield involved the FBI distributing an advertised secure phone through a controlled company and using it to collect the communications of criminal organizations, leading to more than 800 arrests.

So, besides Qubes OS having such significant hardware limitations, it makes supply-chain attacks even easier because it's an operating system that relies on Intel's and AMD's microcode/virtualization technology. Compromising that would compromise all users of this operating system. I'm not saying Qubes OS is the only OS vulnerable to hardware backdoors; in fact, all operating systems are, but Qubes OS is the MOST vulnerable to this type of thing. A Linux or BSD user who doesn't use virtual machines doesn't need to worry about backdoors in the specific CPU's virtualization-technology microcode or about 11 specific devices.

And it gets even worse when dom0 is Fedora-based. Qubes signs dom0 packages and routes downloads through an UpdateVM, so compromising a Fedora mirror alone does not authorize a malicious update. Compromise of the trusted build system, signing key, or an accepted privileged package is still a total system breaking point. Game over. The supposed compartmentalized desktop still has a centralized producer and signing dependency at its most privileged layer. There is no salvation for Qubes OS in pretending otherwise.

7 - Anti Evil Maid and TPM 1.2 requirements

Qubes OS itself does not require a TPM. Its optional Anti Evil Maid (AEM) package requires a TPM 1.2 interface and a working Intel TXT engine; it does not use TPM 2.0. AEM detects selected changes to the measured boot chain. It does not prevent every physical attack, and a Qubes installation without AEM can still use disk encryption and physical controls. Nevertheless, without AEM Qubes lacks the physical-tampering defense that its own design presents for this threat.

But that is not a defense. AEM adds a dependency on TPM 1.2, Intel TXT, firmware, and a separate boot-time security workflow. That adds proprietary code, operational complexity, and more ways for misconfiguration to break boot or weaken security. Firmware or vendor bugs in the TPM or Intel TXT chain can become a persistent compromise point and can subvert the measurements AEM relies on.

Published TPM and firmware vulnerabilities require vendor updates. Hardware that has left vendor support cannot receive those fixes, so the useful lifetime of AEM also depends on continued firmware and microcode maintenance.

A TPM contains a device-specific endorsement key (EK), whose private portion is designed not to leave the TPM. Certificates or attestation records linked to that identity can still enable device correlation; attestation keys and privacy mechanisms exist precisely to avoid exposing the EK directly. I still regard this as a backdoor-like privacy and trust dependency: it introduces a persistent hardware identity and proprietary implementation beneath an operating system marketed to high-risk users. It is not, by itself, proof that every TPM is an intentional backdoor.

Qubes OS could avoid this dependency by providing a physical-attack mitigation that does not require TPM or Intel TXT. Instead, AEM requires hardware and firmware that ordinary users cannot meaningfully audit. That is more code and complexity, and therefore more attack surface.

Owner-controlled firmware, verified boot, detached secrets, tamper evidence, and strict physical custody address parts of the same threat model. None is a drop-in replacement with identical guarantees, but I would rather combine auditable controls than make an Intel-specific measured-launch chain the only official answer.

More on this topic from an authority in the field: Rob Braxman video: "Your Windows 11 Computer's Hidden Spy: The Dark Truth About TPM Chips"

Qubes security guidelines dictate that USB devices should never be attached directly to dom0, since this can result in the entire system being compromised. However, in its default configuration, installing and using AEM requires attaching a USB drive directly to dom0.

What the actual fuck? This is a contradiction in the security model. To be "safe," I am told to expose dom0 in a way that could compromise the entire system.

(The other option is to install AEM to an internal disk. However, this carries significant security implications, as explained here.)

In other words, to obtain this minimum protection I must do something unsafe enough to compromise the system. Wonderful.

This presents us with a classic security trade-off: each Qubes user must make a choice between protecting dom0 from a potentially malicious USB drive, on the one hand, and protecting the system from Evil Maid attacks, on the other hand.

If you want to fuck me, at least pay for dinner. Neither option is a plausible default for a user who wants physical-attack resistance without adding another high-risk step.

8 - Intel ME dependency

Devs: If you cleaned your Intel Management Engine with e.g. me_cleaner while installing coreboot (or libreboot) then you are out of luck. For now you have to choose between cleaning your BIOS and deploying Anti Evil Maid.

This is fucked. AEM's Intel TXT requirement makes it incompatible with systems whose Management Engine firmware has been sufficiently disabled by tools such as me_cleaner. Qubes therefore makes users choose between reducing a backdoor-like proprietary subsystem and deploying its principal Anti Evil Maid mechanism.

Intel Management Engine (ME), now commonly described as part of the Converged Security and Management Engine (CSME), is a privileged firmware subsystem separate from the host operating system. "Ring -3" is an informal security-community label, not an architectural CPU ring. Intel Active Management Technology (AMT) uses CSME on supported vPro systems to provide out-of-band management. ME is widespread; remote AMT networking is a separate capability that must be present and provisioned. The relevant properties are concrete:

  1. ME operates while the host processor is active. Configured AMT platforms can also remain manageable in supported sleep or soft-off states while connected to AC power. Intel's documentation states that AMT is not active in sleep or off states on battery power.

  2. Provisioned AMT uses the platform's wired or supported wireless adapter for out-of-band access. Depending on configuration, it can share the host address or use separate network settings; a distinct MAC and IP address are not universal properties of every ME installation.

  3. AMT implements a management channel independent of the host OS and supports functions such as remote power control, provisioning, firmware configuration, and, on supported systems, keyboard-video-mouse redirection.

  4. In out-of-band mode, provisioned AMT responds to management traffic, enabling diagnosis and remote access. On systems where an administrator has provisioned those features, the management plane operates below the host OS and remains reachable when the OS is unavailable. That is an extraordinary amount of authority to place in proprietary firmware beneath Xen.

    Intel has published serious CSME and AMT vulnerabilities, including the remotely exploitable AMT authentication flaw INTEL-SA-00075. These vulnerabilities affect the platform below Qubes and Xen; AEM's TXT requirement makes that firmware layer part of its measured-launch dependency.

    Platform documentation on Intel AMT and ME:

    • Getting Started with Intel Active Management Technology (developer guide)
    • Intel AMT support article
    • Dell Latitude XT2 Administrator's Guide (PDF)

    AMD's Platform Security Processor is another privileged firmware subsystem, but that does not justify lazily claiming it has Intel ME's independent network-management path. Coreboot and Libreboot can replace or reduce parts of the vendor boot stack on supported hardware; they cannot generally remove firmware required inside the silicon. Their advantage over UEFI Secure Boot is inspectability and owner control, whereas Secure Boot verifies an authorized chain without making that chain auditable. Libreboot GRUB hardening documentation

    A vulnerability in Intel CSME or AMD PSP does not automatically expose VM data. Code execution in a sufficiently privileged firmware component can nevertheless bypass assumptions made by the hypervisor and operating system, compromising the entire device. That is why these subsystems belong in the platform threat model.

More on this topic from an authority in the field: Rob Braxman video: "Intel IME Problems Haunting Us 7 Years Later!"

The truth is that a sufficiently capable physical attack on the device is usually game over. TPM, and especially Intel ME, cannot save you from arbitrary hardware compromise. The goal should be to protect the operating system and data through full-disk encryption, verified boot or filesystem policy such as NetBSD Veriexec, immutability, and kernel hardening. Moving a disk to another computer is safe only if the data remains encrypted and the compromised platform never obtained its keys.

There is no guarantee that TPM, Intel ME, or proprietary firmware code was not compromised before you bought the computer. There is also no meaningful way for ordinary users to verify their reliability. What is guaranteed is that these components add attack surface and more places for malware to hide.

Does Qubes use full disk encryption (FDE)?

By default, Qubes OS uses LUKS/dm-crypt to encrypt everything except the /boot partition.

That is why I describe Qubes OS as vulnerable to physical attacks while depending on two backdoor-like components to "be secure." Meanwhile, several Linux systems support encryption of the /boot partition, or could support it with the right file system. Other operating systems have (or can have) similar protections too, including GrapheneOS, OpenBSD, NetBSD or any Linux distro with GRUB as a bootloader.

Encrypting /boot does not, by itself, solve pre-boot tampering, because firmware still has to obtain or verify the code that unlocks it. My objection is not that another system magically eliminates platform trust; it is that AEM adds a complex Intel-specific trust chain to a platform that was already too complex.

9 - Weak fit for server workloads

Qubes OS is a poor fit for server use. A system that claims serious security should also hold up in reliability-focused server contexts.

Server-oriented operating systems are often treated as more secure than their desktop-focused relatives for a reason. Windows Server is much stronger than regular Windows, Red Hat Linux is stronger than Fedora, and Ubuntu Server follows the same pattern. FreeBSD is very strong, and OpenBSD is the most secure BSD and one of the most secure operating systems ever made. They all have something in common: they were built with server needs in mind. If an operating system is bad or useless for servers, that is a serious warning sign. RHEL, FreeBSD, and OpenBSD can still be used on desktops.

Server quality is not optional for a system that aims at security. It requires availability, integrity, scalability, stability, and reliability. Those qualities naturally support security. 10 - Networking exposure: trust in NetVMs and the split-driver model

Qubes centralizes network access in one or more network-facing qubes (NetVMs). A domain such as sys-net owns the physical device and its driver; client qubes use a Xen virtual-network frontend, while a backend in the provider qube forwards their traffic. This moves physical network drivers out of dom0 but creates an explicit frontend/backend boundary.

NetVMs are the primary external attack surface. Any remotely exploitable flaw in a network-facing qube (browser rendering engine, SSH, Tor client, VPN daemon, kernel network stack) or in the paravirtualized network device frontends can be used to pivot toward the hypervisor or other qubes. Split drivers reduce driver code in dom0, but expose complex device-frontends and device-backend channels (hypercalls, shared memory, event channels) that have been the vector in many hypervisor-escape designs. Network-facing qubes routinely need wide protocol stacks and third-party code (wireless firmware, userland VPNs, DNS, TLS libraries), all large, frequently changed attack surfaces.

Remote exploitation of NetVMs can lead to persistent compromise of network qubes and staged attempts at privileged escapes, data exfiltration, or manipulation of other qubes' network traffic. For attackers, NetVM is the obvious target: it is exposed, important, and fragile.

Qubes OS could improve this by supporting alternative NetVMs such as OpenBSD, hardened Linux, pfSense, and OPNsense. Users can also move parts of the network stack to an external appliance, such as a physical router or firewall, to reduce local exposure. But at that point, though, I would rather use a different OS entirely.

11 - Forensics, logging, and incident response limitations

Qubes' compartmentalization and disposable-qube model complicate centralized, tamper-evident logging and post-incident forensic analysis, reducing assurance after a suspected compromise.

Effective incident response relies on reliable logs, chain-of-custody for evidence, and the ability to reconstruct an attacker's actions. Qubes encourages ephemeral qubes and per-VM storage; by default, logs are scattered across filesystems in different security domains and may disappear with disposable qubes. A compromised domain can falsify its own application logs before they leave the domain. This makes system-wide correlation difficult without providing the amnesic-session guarantees for which Tails was designed.

This can leave users unable to tell whether their system has been compromised. Instead of reducing damage, the model can make the attacker harder to see and therefore more comfortable staying inside the environment.

After a breach, investigators may find incomplete telemetry, missing cross-qube event correlation, and lack of secure, centralized audit trails. That reduces the ability to determine scope, persistence, and exfiltration, and it complicates proving whether a host-level compromise occurred (hypervisor/dom0) versus a guest compromise. For high-assurance environments this weakens incident handling and forensic confidence. In the worst case, malware can remain active without the user's knowledge because the evidence needed to prove compromise was never preserved. That is not a small weakness.

Mitigations have limits. Best practice is to forward immutable, signed logs off-host to a remote collector under operator control (write-once storage or secure SIEM); use cryptographic attestation where possible; and maintain dedicated, high-trust audit qubes with strict ingestion policies. These measures add operational complexity and still require careful threat modeling to avoid introducing new attack channels. At that point, I would rather look for something simpler and stronger.

16 - Terrible against zero-day attacks

A zero-day (also known as a 0-day) is a vulnerability or security hole in a computer system unknown to its developers or anyone capable of mitigating it. Until the vulnerability is remedied, threat actors can exploit it in a zero-day exploit, or zero-day attack.

Zero-day vulnerability on Wikipedia

Qubes OS offers good damage control for failures in guest VMs, but its large virtualization-based TCB (Trusted Computing Base) makes it structurally more vulnerable to zero-days attacking privileged components than alternatives with smaller TCB, focus on correctness, and aggressive mitigations (GrapheneOS, OpenBSD, hardened/enterprise Linux distros). Here I will return to some points already discussed previously, but with the single goal of proving one more point.

Qubes relies on compartmentalization via virtualization (Xen, dom0, VMs with separate privileges) as the main layer of defense, which can be good for reducing the individual impact of known vulnerabilities when the attack targets a guest VM and the goal is to limit its blast radius. But defense against zero-days depends on the probability of occurrence and the ease with which a failure can escape the box in which it is located; at this point Qubes loses completely.

Qubes' own security-critical code inventory includes Xen, xenstore and block backends, dom0-side qrexec, GUI and audio components, the memory manager, and selected RPC services. Containing an ordinary app-qube compromise is a real benefit. My argument is that this benefit is not a complete security model and becomes irrelevant when the unknown bug is in shared privileged infrastructure.

First, the hypervisor and the set of I/O drivers (firmware, controllers, devices) remain large privileged code written mostly in C and assembly, without formal verification. A zero-day that allows code execution on the hypervisor or DMA (Direct Memory Access) support can escape from a VM to dom0 or the hypervisor itself, compromising all compartments at once. The complexity of the entire Qubes OS together leads to a greater likelihood of bugs and certainly leads to a larger attack surface, especially when it comes to memory management.

If you are thinking, "It's simply not possible because Xen runs as a kernel on the system and has only 660 kLoC," then you do not see things as they are.

The platform firmware loads Xen and the administrative domain, dom0. Dom0 manages the other domains and intentionally has no network interface, which removes a major direct attack path. App qubes still run complete guest kernels and userlands, but all of that guest code is not automatically part of the TCB for every other qube. The cross-domain TCB is the code and hardware that process guest-controlled input or enforce boundaries: Xen, hypercalls, event channels, grant tables, virtual devices, backends, qrexec, GUI services, dom0, the IOMMU, and firmware. That is still a gigantic tangle of privileged interfaces. A guest does not own Xen merely because it calls a hypercall, but a flaw in one of those interfaces can turn guest control into system control.

Second, the aggregate attack surface of Qubes is high. In addition to everything said before, there is the kernel(s) of multiple exposed hardware templates and drivers, IPC, hypercalls, grant, backends, control domains, grant mappings, emulation, firmware (TPM, Intel ME, Intel-VT/AMD-V), PCIe/Thunderbolt, unprotected /boot partition and more - more code means more statistical probability of exploitable unknown bugs. Each component is an additional source of zero days; Qubes' "many moving parts" architecture increases the total surface area compared to systems with deliberately smaller TCBs.

A direct attack on the Xen hypervisor through a domU is far from the only way to compromise the entire system. Full-system compromise paths include anything that can reach dom0, Xen, or another trusted service with a bug or overly permissive policy. The big ones are: a Xen escape from an infected domU; a bug in dom0 (outdated Fedora) itself; a bug in qrexec/RPC handling; a bug in the GUI stack; and attacks through device-facing services like network, USB, audio, or storage backends. The file-copy, clipboard, GUI forwarding, and device qubes are the other common routes. None of these is inherently "safe"; the paths can only be made narrower and policy-controlled.

Third, modern mitigations (ASLR, W^X/NX, KARL, KPTI, retpolines, SELinux, namespaces, and others) raise exploit cost through correctness, isolation, and randomization. Qubes inherits mitigations from Xen, Linux, Fedora, Debian, and the applications in each qube, so it is false to say the installed system has none. The contradiction I reject is the claim that these approaches cannot provide reasonable security while Qubes itself necessarily depends on them. Compartmentalization limits authority after compromise; it does not make code correction and exploit mitigations unnecessary.

Fourth, alternatives like GrapheneOS (designed for a hostile environment at the user and mobile kernel level) or OpenBSD (emphasis on code auditing and mitigation by default) reduce the chance of many zero-days being exploitable by having smaller stacks, more aggressive hardening policies, and less dependence on proprietary drivers; Linux implementations like Secureblue aim to protect not only against known but also unknown vulnerabilities (the same goes for the other two operating systems mentioned above), reducing the attack surface and making elevation of privilege exploits much more difficult in principle.

Fifth, Qubes OS is betting that exploitable zero-days will be rare in Xen and the other privileged attack surfaces. That is a terrible bet. Newly discovered software and firmware vulnerabilities require fast, predictable patches, and Qubes cannot independently patch components maintained by Xen and its other upstream projects. Enterprise operating systems such as RHEL, AlmaLinux, Rocky Linux, and Ubuntu, and systems focused on bug prevention and correction such as OpenBSD and GrapheneOS, provide a stronger basis for finding, fixing, and mitigating unknown vulnerabilities before they reach the end user.

Finally, the Qubes security model assumes that compartmentalization will be the primary security layer. That is practical, but it is a horrible bet against a world that doesn't act as its developers think. When an effective zero-day arises against the hypervisor, or against privileged subsystems, compartmentalization does not fix or randomize the bug - it simply depends on the bug never existing or not being scalable. In comparison, systems with lower privileged TCB, audited code/smaller attack surface, and mitigations offer greater structural resistance to zero-day attacks.

"Qubes OS allows you to use OpenBSD and all these other operating systems inside qubes," you might say. No, not as an officially supported template. Qubes officially supports Fedora and Debian templates. Whonix templates are supported by the Whonix Project; Windows qubes can be installed, but Qubes cannot distribute a preconfigured Windows template. Other community templates have separate maintainers, and the Qubes OS Project neither tests them nor supplies their updates. That further diminishes trust.

In all cases, the Qubes OS Project does not provide updates for these templates.

In addition, these templates may be somewhat less stable, since the Qubes developers do not test them.

Qubes OS templates documentation

Qubes OS is not even stable by default and yet they offer even more unstable ways to use it? How would this increase security (especially against zero-days)? You can't take this operating system seriously, not if you're like me and value security first.

Installing another operating system adds code inside that guest, not automatically to the TCB of every other qube. The cross-domain risk comes from the additional hypercalls, virtual devices, qrexec services, and user-authorized transfers exposed to guest-controlled input. You cannot accumulate privileged interfaces and assume they create security merely because each has a compartment label. What protects the hypervisor and its backends from a malicious guest is still the correctness and hardening of Xen and those interfaces.

Qubes OS could improve this point with a much smaller verified or microkernel-like privileged base and zero guest VMs by default. seL4, L4 systems, MINIX 3, and GNU Mach illustrate different approaches, but replacing Xen is not a component swap: Qubes would need new device isolation, virtualization, GUI, RPC, and management implementations. The microkernel label alone proves nothing. The real requirement is a smaller, auditable, correctly implemented privileged base.

Conclusion

Qubes OS is not the best, or even a good, alternative for those seeking security. Without security, long-term anonymity is impossible. This OS is for people who want quick and easy control of virtual machines for testing or casual use, and for those willing to trade security for the ability to juggle many profiles across work, privacy, and other contexts.

Some criticisms in this article also apply to other Linux distributions and operating systems, but only Qubes OS combines all of them at once. It is unique in being such garbage. The following section presents far stronger alternatives for security and isolation.

For anonymity alone, Tails is superior, while Whonix is stronger for security. Whonix can run under KVM on Linux systems that may be safer than Qubes OS; in my assessment, KVM is a better security choice than Xen for that use.

Qubes OS can contain some ordinary desktop compromises, but that limited benefit does not justify presenting it as the strongest security design. Xen and dom0 form a concentrated TCB (Trusted Computing Base) with ongoing XSAs (Xen Security Advisories), while paravirtualized interfaces make VMs easy to fingerprint and enlarge the guest-to-hypervisor attack surface. Qubes inherits Linux kernel and driver code through Fedora and Debian, depends on modern CPU microcode, and supports a narrow set of certified hardware. Disposable qubes can reduce persistence inside one guest; they do not remove the privileged attack surface beneath it. For high-assurance, server, high-threat, or enterprise use, where a smaller auditable TCB, formal hardening, long support windows, and headless management matter, this desktop-centric design is a misfit, not a solution.

An operating system designed by people who don't believe in security through clean code, bug fixes, and mitigations cannot be trusted, because its developer base is not trustworthy.

If your threat model doesn't involve serious and persistent adversaries, powerful organizations, or state actors, Qubes OS might be good for you. If you prioritize compartmentalization over stability and want to manage multiple aspects of your life simultaneously without worrying about servers, zero-day vulnerabilities, or hardware compatibility issues, then Qubes OS might be perfect for you. If your enemy consists of amateur hackers and common criminals, Qubes OS might be sufficient for you. It is appropriate against less capable adversaries, such as script kiddies and opportunistic criminals.

Reality check: Qubes suits solo enthusiasts trading manageability, stability, compatibility, predictability and security for experimental compartmentalization.

Points to consider

I know that VMs bring compartmentalization at the OS level, and that they make many things easier. But user-level sandboxing can be very secure while also being much less complex. An escape from this kind of sandboxing limits an attacker to the user's context; such an escape typically grants only user privileges, not full system control.

There is no such thing as perfect security, much less perfect isolation, but there is security greater than Qubes OS.

I do not trust virtual machines as absolute security boundaries, and neither should you. OpenBSD's vmm is the hypervisor I trust most because its deliberately narrow feature set, userland device model, and process compartmentalization expose less host code and authority to a guest.

OpenBSD added vmm after years of public skepticism from Theo de Raadt about hypervisor security. The OpenBSD vmm FAQ documents its narrow feature set and lists these unsupported features:

  • Graphics
  • Snapshots
  • Guest SMP support
  • Hardware passthrough
  • Live migration across hosts
  • Live hardware change

For workloads that need those broader features, use KVM, Hyper-V, bhyve, or VMware ESXi. They have different architectures and patch histories, so feature count alone does not prove a security ranking, but I would choose any of them before Xen.

In terms of exploit mitigations, NetBSD supports a good number of modern features: W^X (in both userland and the kernel), Userland ASLR, Kernel ASLR, SMEP, SMAP, and a variety of other internal kernel bug detection features.

  • To learn more about its security features and hardening:
    • NetBSD security(7) manual page
    • NetBSD wiki: Security

NetBSD provides Linux binary emulation on supported architectures, and pkgsrc includes Wine on supported platforms. Compatibility is narrower than FreeBSD's and must be verified per application.

6 - Alpine Linux

Alpine Linux is a security-oriented, lightweight Linux distribution based on musl libc and busybox. It was designed with security in mind. All userland binaries are compiled as Position Independent Executables (PIE) with stack smashing protection. These proactive security features prevent exploitation of entire classes of zero-day and other vulnerabilities.

The Alpine Linux project

Alpine uses musl, BusyBox, and OpenRC instead of the common glibc, GNU Core Utilities, and systemd stack. Its minimal installation omits many interfaces and services present in larger distributions, reducing the default attack surface. PIE and stack protection raise exploit cost but do not prevent every exploit or remove the underlying defects. Alpine is essentially "Linux if it were good," and it remains an excellent base for small containers.

  • Alpine has native support for hardened_malloc, GrapheneOS's malloc implementation. Install it. Alpine wiki: Hardened malloc
  • For some hardening: Alpine wiki: Securing Alpine Linux

7 - Artix Linux Hardened

Artix is Arch Linux but good (doesn't have systemd).

Artix uses real init systems, because PID1 must be simple, secure and stable.

The Artix Linux project

Arch Linux is an independently developed, x86-64 general-purpose GNU/Linux distribution that strives to provide the latest stable versions of most software by following a rolling release model. The default installation is a minimal base system, configured by the user to only add what is purposely required. Arch Linux defines simplicity as without unnecessary additions or modifications.

About Arch Linux

Artix combines its own repositories with access to much of the Arch ecosystem and the community-maintained AUR. Unofficial repositories such as Chaotic-AUR and BlackArch expand that range further but add independent maintainers and signing policies to the trust model. A minimal Artix installation can expose fewer services than a large desktop distribution, although package count alone says nothing about the deployed attack surface.

Be careful with packages from unofficial repositories such as the AUR. They are community-maintained, and malicious packages have appeared before. Always check the maintainer, creation and update dates, build origin, repository signature, and keyring.

  • Using this distribution also gives you the Arch Wiki, which is probably the best and most complete documentation in the Linux world. Arch Wiki
  • For proper hardening (you will take some days):
    • Arch Wiki: Security
    • Madaidan's Linux hardening guide
  • hardened_malloc is available for download in the AUR, but I don't know if there's a guide on how to configure it in Arch: AUR package: hardened_malloc

8 - FreeCORE

The FreeCORE project

FreeCORE is the independent continuation of TrueNAS CORE 13.3 after upstream CORE development ended. It keeps the operating system on the foundation that made it compelling in the first place: FreeBSD and OpenZFS. The project rebased that lineage on FreeBSD 15, publishes its own stable update train, and supports both a fresh installation and an in-place upgrade from TrueNAS CORE 13.3.

This is what I want from a storage operating system: a coherent BSD base, ZFS, jails, conservative administration, and no forced migration to a Linux appliance merely because another vendor abandoned the FreeBSD edition. FreeCORE 15.0 also removed vendor telemetry and the former enterprise-licensed features, replaced OpenVPN with WireGuard, and added WebAuthn for the web interface.

If your goal is to manage long-term data in a secure, stable, and reliable way, FreeCORE is one of the best options. It is excellent for servers and long-term storage. In my opinion, OpenZFS is the best filesystem for this job because it combines end-to-end checksums, snapshots, replication, compression, and native encryption. Compression savings depend entirely on the data and must not be used to promise physical capacity.

9 - Kicksecure

Kicksecure is a free and open-source Linux distribution that aims to provide a highly secure computing environment. It has been developed from the ground up according to a formidable and time-proven defense-in-depth security design. In the default configuration, Kicksecure provides superior layered defenses of protection from many types of Malware.

Kicksecure is a complete computer operating system. Numerous applications come pre-installed with safe defaults which can be used immediately upon installation with minimal user input.

Kicksecure is an extensively reconfigured Debian-based system focused on security, and it is also the base for Whonix. It is my recommendation for users who want Debian's administration model with stronger defaults. I place it below Secureblue and alongside Alpine for default Linux security; that ordering is my assessment of their shipped policies, not a published comparative benchmark. The Kicksecure project

These are the best Linux operating systems for businesses that want enterprise security, tested updates, binary compatibility with the RHEL ecosystem, long lifecycles, commercial or third-party support, standards compliance through SELinux, Secure Boot, and FIPS-oriented partners, and predictable operations. They also keep costs controlled while providing a stable experience for advanced users and administrators.

11 - Proxmox VE

Proxmox Virtual Environment is a complete open-source platform for enterprise virtualization. With the built-in web interface you can easily manage VMs and containers, software-defined storage and networking, high-availability clustering, and multiple integrated tools through one system.

The Proxmox VE project

Proxmox VE is my recommendation when the real requirement is serious server virtualization instead of Qubes OS's single-user desktop experiment. It builds on Debian, uses KVM for hardware-assisted virtual machines, and offers LXC for workloads that can share the host kernel. LXC is a weaker boundary than a VM against a kernel exploit, while KVM and Xen expose different privileged interfaces; the labels alone do not prove one universally safer.

The operational model destroys Qubes OS for server use. Proxmox manages conventional hosts, full VMs, storage, networking, backups, and clusters as one platform. It offers commercial support and SLAs, live migration, high-availability clustering, software-defined networking, encrypted and deduplicated backups, multi-factor authentication, and role-based access control. Qubes cannot provide these workflows because its architecture is desktop-only.

Proxmox still has a substantial attack surface: KVM, QEMU, paravirtualized virtio devices, the management API and web interface, LXC, storage, clustering, and optional Ceph services all require hardening and prompt updates. It replaces the Qubes trust model with a different one; it does not magically abolish the hypervisor or device model.

For people who want virtualization-based server isolation, commercial support, high availability, and managed backups, Proxmox VE solves the correct problem. It does what Qubes OS pretends it can do in server arguments, but as a real enterprise platform.

  • HardenedBSD is a FreeBSD fork focused on security, with hardening work that differs from both FreeBSD and OpenBSD. It could be one of the most secure operating systems, but I do not understand it well enough to rank it confidently, and its small development community and confusing project presentation make it difficult to evaluate. I would welcome a user or developer explaining it in greater detail. The HardenedBSD project

  • GrapheneOS is a privacy- and security-focused mobile OS with Android app compatibility, developed as a nonprofit open-source project. It is much more reliable and secure than Qubes OS, and more secure than any Linux distribution, but it supports only selected Google Pixel devices. The GrapheneOS project Profiles can be separated completely, each with its own apps and data, and offline profiles can be created with strong data isolation. Verified boot, hardware-backed key storage, exploit mitigations, and a hardened application sandbox protect the common platform. That is a safer, simpler, less complex form of isolation than Qubes OS offers.

  • NixOS has everything needed to be one of the most secure Linux distributions, if it weren't for that problematic systemd. Its declarative system model, reproducible package builds, atomic generation changes, and rollbacks are technically excellent. Configurations can span many Nix modules rather than one file, and declarative state does not make the selected services secure. It also has an incredible repository and package manager. The NixOS project However, a light shines in this Linux distro: SixOS. "sixos: a nix os without systemd":

  • Sculpt OS and Genode OS have an extremely strong security architecture built around the Genode component framework. Genode can use seL4, a formally verified microkernel, among other kernels. These are not yet general-purpose replacements for most readers, but they have enormous potential. The Genode OS Framework project

  • Redox OS is a complete Unix-like, microkernel-based operating system written from scratch in Rust, with a focus on security, reliability, and memory safety.   • Linux From Scratch (LFS) is not my recommendation. It is extremely complex and unrewarding, and it does not automatically provide more security than a properly built Gentoo system. Maintenance is difficult and risky because you are effectively creating your own distribution. Unless you are a wizard with months of free time and advanced Linux knowledge, stay away. I have done it; it was fun, but it was not worth it.

  • Openwall GNU/*/Linux could be interesting, but I need more research before making a firm recommendation. Openwall GNU/*/Linux
