Operating systems

Why I stopped using Linux

Written by FlyWithMe (a SimpleX Chat user) - Updated August 16, 2026

After thirteen years with Linux, I left because its security model, integration burden, operational complexity, and project culture no longer met my requirements. This article explains that decision and identifies the alternatives I consider superior.

This is a personal technical critique based on thirteen years of using Linux and repeated attempts to harden it. The linked examples support the specific claims; they are starting points for readers who want to inspect the underlying projects and decisions themselves.

This is not a survey of every Linux distribution. It addresses the failures that determined my decision.

Security concerns

Security is a primary requirement for every system I use. Features and convenience do not compensate for an architecture I cannot harden or audit to my satisfaction.

I abandoned Windows 10 for security reasons and stopped using Linux on my computers in 2024 for the same reason. Linux served me for more than thirteen years, but its kernel and conventional desktop stack were not designed around the security priorities I now demand.

If you don't treat security like a religious fanatic, you are going to be hurt like you can't imagine. And Linus never took seriously the religious fanaticism around security,

Dave Aitel, a former National Security Agency research scientist and founder of Immunity, a Florida-based security company.

There is a sharp irony here: the NSA, an institution built around signals intelligence and surveillance, originated SELinux, one of the Linux ecosystem's most consequential mandatory-access-control systems.

The people who care most about this stuff are completely crazy. They are very black and white,

Linus Torvalds.

Security in itself is useless... The upside is always somewhere else. The security is never the thing that you really care about.

Linus Torvalds.

I personally consider security bugs to be just normal bugs. I don't cover them up, but I also don't have any reason what-so-ever to think it's a good idea to track them and announce them as something special.

Linus Torvalds.

Torvalds has engaged in an occasionally profane standoff with experts on the subject. One group he has dismissed as "masturbating monkeys." See the Linux kernel mailing-list thread.

In blasting the security features produced by another group, he said in a public post, "Please just kill yourself now. The world would be a better place."

Everything above can be read here: Net of Insecurity: The kernel of the argument (Washington Post)

These statements document Torvalds's resistance to treating security defects as a separate class and his hostility toward some security contributors. They do not describe every kernel developer, but they explain why I reject the claim that Linux has always treated security as a first-order design constraint.

What about security-focused Linux operating systems like Qubes OS? Linux can be very secure

A common objection from Linux users.

My separate Qubes OS analysis explains why adding VM compartmentalization does not remove the Linux, Xen, firmware, and operational risks beneath that boundary.

The Linux distribution that I consider the most secure by default is Secureblue. The development team takes security very seriously, and they don't mind trading usability for security. Let's see what they say about Linux:

Who is secureblue for?

secureblue is for those whose first priority is using Linux, and second priority is security. secureblue does not claim to be the most secure option available on the desktop. We are limited in that regard by the current state of desktop Linux standardization, tooling, and upstream security development. What we aim for instead is to be the most secure option for those who already intend to use Linux. As such, if security is your first priority, secureblue may not be the best option for you.

The Secureblue website

Secureblue applies the strongest default hardening I have examined in a general-purpose Linux distribution. Its Fedora Atomic base, hardened kernel configuration, mandatory access control, and application policies improve the system substantially. They still operate within the interfaces and architectural constraints of the upstream Linux platform.

Conventional desktop Linux requires additional hardening. ChromeOS reduces variation through verified boot, automatic updates, and tight control over supported hardware; Secureblue hardens a more conventional general-purpose environment. Neither distribution policy can remove every upstream kernel interface or redesign the kernel beneath it. Madaidan's Linux (in)security

The Linux kernel and a complete GNU/Linux distribution contain an enormous volume of code. Debian's own source archive statistics exceed one billion physical source lines, while the kernel alone contains tens of millions. Source size is not identical to attack surface: only reachable interfaces and code paths form the attack surface of a given deployment. Size still increases the code that maintainers must review, integrate, compile, and patch.

Sources:

  • Debian micronews: source archive statistics
  • Debian source statistics

OpenBSD develops a deliberately bounded base system as one source tree, rather than treating an entire third-party package archive as part of the operating system. Research and specialized systems such as Redox, Sculpt, Tock, and LionOS reduce or restructure privileged code in different ways. A smaller codebase strengthens auditability only when the removed code would otherwise sit inside the trusted computing base or expose reachable interfaces; raw line counts do not prove security.

This independent Linux hardening guide documents a useful baseline, but readers must verify every recommendation against current kernel and distribution documentation.

Complexity

My experience spans Debian, Ubuntu, Fedora, openSUSE, Arch, Manjaro, CachyOS, Artix, Gentoo, Qubes OS, Exherbo, secureblue, Alpine, and Linux From Scratch. This criticism comes from administering, rebuilding, and hardening those systems, not from a brief encounter with one desktop distribution.

The recurring problem is system-wide complexity, not desktop appearance. A Linux administrator must reconcile kernel parameters, init and service policy, network configuration, privilege escalation, mandatory access control, package scripts, boot configuration, and distribution-specific filesystem conventions.

OpenBSD, FreeBSD, and NetBSD exposed how much integration work I had accepted as normal. Their base-system documentation describes a coherent release, while Linux documentation is divided among the kernel, distribution, init system, network stack, package manager, and individual upstream projects.

systemd concentrates service management, logging, login sessions, networking, DNS, time synchronization, containers, and other functions in one tightly coupled project. I reject that scope because a defect or incompatible change crosses subsystem boundaries that separate tools would keep independent.

Achieving minimally pleasant hardening on Linux is extremely difficult and is not viable for the vast majority of users. I spent weeks hardening Arch Linux, two months on Gentoo, and six months on Linux from Scratch. The result still depended on maintaining custom systemd units, kernel policy, sandbox rules, and package-specific exceptions, an unreasonable permanent workload for one administrator.

Arch and Gentoo remain the most hardening-friendly conventional distributions I used: Arch documents the system exceptionally well, while Gentoo exposes toolchain, libc, init, kernel, and package choices that binary distributions fix in advance.

That flexibility is real, but the continuing integration burden is the price. I no longer accept that price on my primary systems.

Instability

I require updates to preserve a working system without repeated repair. Neither Debian stable nor Ubuntu LTS met that operational requirement in my deployments.

A long support lifecycle and runtime stability are different properties. Lifecycle policy states how long a release receives maintenance; operational stability measures whether supported updates preserve documented behavior and keep configured workloads running.

In my installations, Arch proved more predictable than Ubuntu LTS and Debian stable. Package additions and supported updates still caused failures often enough that I had to treat rollback and manual repair as routine maintenance. That is an account of my systems, not a claim that every Linux installation inevitably breaks.

In the Linux communities I used, routine breakage was commonly treated as a normal cost of maintaining the system. I reached a point where I could only achieve pleasant stability on Linux with extremely minimalist distros and configurations to the point where I didn't even have security (no MAC, Wayland, sandboxing, firewall, kernel parameters, boot config or any hardening at all).

RHEL, Azure Linux, and Ubuntu invest heavily in release engineering and compatibility, but they must integrate independently governed upstream components across broad hardware and software combinations. Android and ChromeOS obtain stronger platform consistency by controlling the supported hardware, update path, and application model more tightly than a conventional distribution.

My conclusion is narrower and better supported: across rolling, stable, source-based, and LTS distributions, Linux never delivered the operational stability I require.

Centralized decentralization (Or would it be decentralized centralization?)

Linux's modular ecosystem once promised meaningful substitution among userlands and system components. In mainstream distributions, dependence on GNU interfaces, systemd, D-Bus, and a small group of heavily funded upstreams has narrowed that practical choice. What was presented as decentralized integration now depends on several central projects.

Linux is a kernel, so distributions can assemble radically different systems around it. Most desktop and server distributions instead share the same kernel, GNU libc and utilities, systemd service architecture, D-Bus interfaces, and desktop stack. Repositories, release engineering, defaults, and package managers still matter, but they do not create independent operating-system architectures.

Kali is a specialized Debian derivative with a rolling repository, penetration-testing tools, and task-specific defaults. Those changes serve its intended workflow, but they do not replace the Linux kernel, GNU userland, service architecture, or the underlying security model. The same distinction applies to Ubuntu and Fedora: distribution policy changes the assembled system without creating a new operating-system architecture.

Red Hat, now owned by IBM, funds development across Fedora, systemd, SELinux, libvirt, GNOME, and other infrastructure used far beyond its own distributions. That is not ownership of Linux, and each project has its own governance. It does give one vendor substantial engineering influence over components that other distributions cannot replace without major integration work.

Alpine, Void, Chimera, and configurable systems such as Gentoo prove that alternatives remain possible. They can replace systemd, glibc, GNU coreutils, or all three, although third-party applications and desktop environments often pull the system back toward interfaces used by mainstream distributions. Removing those central dependencies is valuable, but it does not turn a distribution into an integrated BSD base system.

My second criticism concerns integration. The Linux kernel and its userland are developed by separate projects with different release schedules, compatibility policies, and security models. Distributions must integrate those components and resolve the resulting policy and lifecycle conflicts. That division increases complexity and makes system-wide invariants harder to define and enforce.

The result is centralized dependency on a few dominant components without centralized responsibility for the complete operating system. Linux retains fragmented ownership while losing much of the practical replaceability that fragmentation was supposed to provide.

License

As I already talked about in my other article: the License section of "Why OpenBSD stands alone"

Linux has spent years pulled between community goals and large corporate interests, especially from companies such as IBM that want Linux shaped for enterprise platforms. That pressure damages the Unix philosophy.

A permissive Linux license would not eliminate corporate influence. It would allow vendors to maintain proprietary downstream changes instead of publishing corresponding source when they distribute binaries. The GPL creates an incentive to place reusable changes upstream, where vendors compete to shape the common kernel. Microsoft, Google, Intel, IBM, and other companies therefore contribute both code and policy to Linux.

Intel Is Pushing For 1984-Style Revision Of Words Allowed In Linux Kernel Development And Documentation (Linux Reviews)

I still prefer permissive licenses. They let each recipient use, modify, combine, and redistribute the code without imposing reciprocal licensing on a larger work. They do not guarantee a technically pure upstream, but they make independent downstream development a lawful alternative to winning control over the common project.

Under my definition, freedom includes the freedom to combine code with differently licensed or proprietary work. The GPL deliberately withholds that option when distribution creates a covered combined work. GNU calls this reciprocity; I call it a restriction. That is a value judgment about licensing, separate from the factual question of who governs a project.

BSD, MIT, and Apache licenses still impose notice or other narrow conditions because copyright licenses are legal instruments, not the absence of copyright. They nevertheless preserve far more downstream discretion than the GPL, which is why I rank them higher.

Community

Since 2019, the Linux communities I used have shifted away from the technical focus I found there earlier. Political and ideological tests now enter moderation and project-selection decisions that should be resolved through code, threat models, and maintenance evidence.

I encountered muting, bans, and threats in channels presented as technical forums when participants rejected the administrators' politics. Those incidents do not describe every Linux group, but they explain why I no longer trust the wider community as a technical institution.

The recurring failure was asymmetric enforcement: administrators allowed aligned political speech while treating disagreement as misconduct. That converts software channels into affiliation tests and makes technical standards secondary.

Across Discord, Matrix, social media, and forums, I repeatedly saw technical disputes displaced by ideological tests, personal attacks, and erratic moderation. Those are observable community failures; they do not require diagnosing strangers or speculating about their mental health.

I left because participation became intolerable. Eight years ago, I regarded the Arch Linux community as one of the Internet's most capable technical communities: discussions were specialized, documentation was dense, and expertise was abundant. My later experience did not preserve that standard.

Disagreement is normal; viewpoint-based exclusion from technical channels is not. Projects that invoke "free and open-source software" or "digital freedom" while suppressing dissent contradict their stated values and drive technically capable contributors away.

You are free, but only as long as you agree with them.

A technical community cannot advance when affiliation outranks evidence. My objection to expansive codes of conduct is operational: vague behavioral rules give moderators discretion over technical disagreement and make participation depend on social conformity.

That combination of ideological gatekeeping and discretionary moderation is why I no longer treat the wider Linux community as a reliable technical environment.

Superior alternatives

BSDs

I rank the BSD operating systems above Windows, macOS, and Linux as replacements for a Unix-oriented user. Each BSD develops its kernel and base userland as one product, which enables coordinated releases, documentation, interfaces, and security changes. That coherence is the concrete source of the simplicity and reliability I found missing in Linux distributions.

Further reading on the differences between BSD operating systems:

  • The Main Differences Between OpenBSD, FreeBSD, NetBSD, and DragonFly BSD (Unix Digest)
  • Comparison of BSD operating systems (Wikipedia)

OpenBSD

OpenBSD is now my daily operating system. Its conservative defaults, small base, integrated documentation, and public focus on technical merit make its community the most technically disciplined one I have used.

The OpenBSD project produces a FREE, multi-platform 4.4BSD-based UNIX-like operating system. Our efforts emphasize portability, standardization, correctness, proactive security and integrated cryptography. As an example of the effect OpenBSD has, the popular OpenSSH software comes from OpenBSD.

The OpenBSD project

Be as politics-free as possible; solutions should be decided on the basis of technical merit.

OpenBSD project goals

OpenBSD places security, correctness, and simplicity at the center of its base-system design. My OpenBSD article examines the mechanisms and engineering practices behind that judgment.

Its package collection is intentionally less expansive than the largest Linux and FreeBSD repositories. OpenBSD 7.9 does not ship Wine or a Linux binary-compatibility layer, so applications that depend on those environments require another system.

FreeBSD

FreeBSD was the first system I used after leaving Linux. It is my BSD recommendation for users who need a broader desktop and application compatibility range: it provides Linux binary compatibility, Wine, and work toward Steam support. The FreeBSD Ports Collection now contains more than 36,000 third-party applications, although availability still varies by architecture and package branch.

FreeBSD is an operating system for a variety of platforms which focuses on features, speed and stability. It is derived from BSD, the version of UNIX developed at the University of California, Berkeley. It is developed and maintained by a large community.

About FreeBSD

I have encountered some of the same community problems around FreeBSD, but on a smaller scale. Its base-system engineering and documentation remain technically strong, which keeps it above Linux in my ranking.

Read and strictly follow the handbook during installation: FreeBSD Handbook

NetBSD

NetBSD is an operating system for hackers with an unusually broad hardware range. Its supported ports extend from servers and desktops to embedded systems and machines such as the Nintendo 64, exceeding the architecture coverage of mainstream Linux distributions.

NetBSD is a free, fast, secure, and highly portable Unix-like Open Source operating system. It is available for a wide range of platforms, from large-scale servers and powerful desktop systems to handheld and embedded devices.

The NetBSD project

pkgsrc gives NetBSD a broad, portable package collection. NetBSD also provides Linux binary compatibility on supported architectures, while Wine availability depends on the platform and pkgsrc package state.

Good Linux operating systems?

I encourage readers to leave Linux where a superior system meets their requirements, but hardware and application constraints make that impossible for some users. The following Linux systems still solve specific problems well; none escapes every architectural criticism in this article.

Gentoo

Gentoo is complex and source builds consume substantial time, but it exposes exceptional control over the toolchain, init system, services, package features, and kernel. Careful profile and package selection can produce a small, independently configured system.

My preferred configuration uses a musl profile, OpenRC, and a minimal userland. BusyBox can replace many standalone utilities, but it also consolidates them into one executable and reduces compatibility; that is a size and maintenance tradeoff, not automatic hardening.

Guix (+ Nonguix)

Guix is GNU-centered but avoids systemd and provides a declarative system. Of the Linux communities discussed here, it is the one I find least objectionable.

Guix can be stable and minimal. On common x86 hardware, refusing all proprietary firmware can leave CPU microcode and device firmware unavailable, including vendor fixes for known vulnerabilities. Nonguix supplies those components, at the cost of departing from GNU's free-system policy. Its official repository is Nonguix on GitLab.

GrapheneOS

GrapheneOS is a privacy and security focused mobile OS with Android app compatibility developed as a non-profit open source project. It's focused on the research and development of privacy and security technology including substantial improvements to sandboxing, exploit mitigations and the permission model.

The GrapheneOS project

It's not a Linux distribution, but it is a Linux operating system, and it's the only Linux I use. I really like GrapheneOS, but it is not free from Google's decisions regarding Android and Google Pixel.
