Operating systems

Why OpenBSD stands alone

Written by FlyWithMe (a SimpleX chat user). Inspired by why-openbsd.rocks - Updated August 16, 2026

OpenBSD integrates secure defaults, source auditing, exploit mitigations, privilege-separated daemons, and small base-system implementations. This article explains why that coherent architecture remains superior to hardened Linux, Windows, macOS, mobile systems, and competing BSD designs.

For readers interested in discussing OpenBSD, there is also an independent OpenBSD group on SimpleX Chat. It is not directly related to this website, although its administrators are the same.

As the Fedora Secureblue developers themselves say:

Secureblue is for those whose first priority is using Linux, and second priority is security. secureblue does not claim to be the most secure option available on the desktop. We are limited in that regard by the current state of desktop Linux standardization, tooling, and upstream security development. What we aim for instead is to be the most secure option for those who already intend to use Linux. As such, if security is your first priority, secureblue may not be the best option for you.

  • Linux's current model cannot provide OpenBSD's unified security architecture. A distribution hardens the kernel and userland, but cannot turn their independently governed upstream projects into one auditable base system.

0 - Philosophy

OpenBSD believes in strong security. Our aspiration is to be NUMBER ONE in the industry for security (if we are not already there). Our open software development model permits us to take a more uncompromising view towards increased security than most vendors are able to. We can make changes the vendors would not make.

  • This is different from most operating systems, which were not created with the goal of being the most secure. The Linux kernel was not designed around extreme security from the beginning, and old design choices still affect it. A few Linux distributions aim for security, but they do not rewrite the operating system from scratch; they mostly harden user space and parts of the kernel. Distribution hardening improves Linux, but it does not match the architectural control of OpenBSD, or the BSD family in general, and it does not replace Linux's independently developed kernel and userland with one security architecture.

1 - Library order randomization

In rc(8), libc.so, libcrypto, and ld.so are relinked on startup, so their objects are placed in a random order at boot. This makes return-oriented programming and similar attacks harder, because symbol locations are no longer predictable in the same way.

  • Linux randomizes base addresses, but it does not relink or reorder internal libc symbols at each boot. Internal offsets and gadgets in the same build can remain predictable across machines or boots, so a small infoleak can be enough to locate useful gadgets.

2 - arc4random(3)

OpenBSD has its own cryptographic random number interface. When random input is needed, arc4random is the standard choice. It is an abstraction over a cryptographic pseudorandom generator, currently ChaCha20. The name means "A Replacement Call for Random." Callers obtain random values without managing generator state or choosing a cipher.

3 - First in security implementations

OpenBSD's innovation history records several defaults that appeared there before comparable deployment in other widely used operating systems:

  • The first operating system to integrate post-quantum encryption by default (since April 2022, OpenSSH).
  • The first widely used operating system to provide ASLR by default.
  • The first free operating system to provide an IPSec stack.
  • The first widely used operating system to enable PIE globally by default.
  • The first operating system to enable stack protector system-wide by default.
  • First complete integration and adoption of IPv6, starting Jan 6, 1999. Almost fully operational Jun 6, 1999 during the first OpenBSD hackathon.

These firsts establish a recurring pattern: OpenBSD deploys system-wide defenses as defaults while other operating systems still leave comparable mechanisms optional or unintegrated.

4 - Camera and audio recording

For privacy reasons, the OpenBSD team disabled camera and audio recording for all devices by default in the kernel. This can be toggled on and off with a simple sysctl change, without rebooting.

5 - Chrooted web server by default

OpenBSD's base httpd(8) runs chrooted in /var/www by default and separates privileged coordination from request handling. That boundary is part of the shipped daemon, not an optional deployment recipe. Web servers installed from packages have their own privilege and chroot behavior and must be assessed from their package documentation rather than inheriting this guarantee automatically.

6 - cron(8)

OpenBSD's cron(8) daemon can randomize values (~) and prevent multiple jobs from running concurrently (-s). Preventing conflicts avoids race conditions, simultaneous access to shared resources, and overload caused by multiple instances, reducing the risk of data corruption and load spikes. Randomized offsets distribute synchronized starts and address the thundering-herd problem; they are an availability control, not an access-control boundary.

OpenBSD's version is not a ground-up replacement: it descends from Paul Vixie's implementation and is maintained as part of the coherent base system. Maintaining it there lets OpenBSD audit, simplify, and integrate suitable inherited code instead of choosing between an untouched dependency and a gratuitous rewrite.

The cron(8) manual documents strict checks on the files that can cause commands to execute. User crontabs require mode 0600; /etc/crontab must be writable only by root and must not carry execute, set-ID, or sticky bits. The crontab(1) utility's cron.allow and cron.deny files control who may install user crontabs and fail closed when they cannot be read. The base-system daemon source pledges the scheduler's permitted operations. The job setup code changes to the owner's login class and credentials and checks account approval before executing the command.

The documented crontab(5) extensions put these controls in the base scheduler. Random ranges spread synchronized starts, and -s supplies single-instance execution without importing a large service manager. Random timing is not an access-control boundary, and a scheduled command still runs with its owner's authority. OpenBSD therefore places concrete correctness and availability controls in an inspectable base-system scheduler without misrepresenting them as a sandbox.

  • systemd timers can express randomized delays and prevent overlapping units on Linux (I strongly oppose systemd's design and scope), but these properties depend on the unit's configuration rather than the base cron format.

6.1 - security(8)

OpenBSD includes security(8), a script run by daily(8) that checks for signs of common security weaknesses and mails any output to root. Its checks cover account databases, root's login environment, home and dotfile permissions, changes to files in /etc/changelist, mounted-disk labels and partition tables, package changes, and selected network configuration permissions.

The manual calls security(8) an aid, not complete protection. It moves obvious weaknesses and unexpected changes into routine administration, provided someone reviews the daily reports and maintains the monitored file list.

7 - Defined integer overflows

On OpenBSD, Clang, the default compiler on most architectures, has the -fwrapv flag enabled by default. GCC also does not include -fstrict-overflow in the -O2 optimization option. This tells the compiler to treat signed integer overflows as defined, preventing optimizations that remove security-critical overflow checks. This is another example of sane defaults.

8 - doas(1)

OpenBSD added doas instead of importing sudo into the base system. doas covers common privilege-escalation workflows with a smaller command surface and policy language. The resulting program and configuration are short enough to review directly.

The official OpenBSD 5.8 upgrade guide described both the program and its configuration as much simpler than sudo. The doas.conf(5) grammar expresses policy with permit and deny rules that constrain the identity, target user, command, and exact arguments; unmatched requests are denied. This is more than aesthetic minimalism: administrators receive a compact, directly inspectable policy while sudo's long tail of compatibility behavior out of the base system. A bad rule can still be unsafe, but OpenBSD provides the clearer foundation.

This is a minimal doas.conf configuration:

permit <user> as root
permit root

The first rule grants the named user broad root access after authentication; a production policy should add cmd and args constraints wherever the workflow permits them. Even this broad example exposes its authority in two readable rules.

  • Portable implementations make doas available on Linux, although integration varies by distribution. Secureblue instead removes setuid-root sudo, su, and pkexec in favor of systemd's run0. That is a different design, but it reflects the same decision to reduce the authority exposed through traditional setuid tools.

9 - freezero(3)

The libc function freezero(3) deallocates an object while guaranteeing that the specified memory range is explicitly discarded. Cached objects are cleared with explicit_bzero(3), and pages returned to the kernel are disposed through munmap(2). The API makes secret erasure an explicit part of deallocation.

  • Other systems provide combinations of explicit_bzero, secure-clearing functions, and allocator APIs. OpenBSD's distinction is the direct freezero contract in libc and its use throughout the same base tree.

10 - httpd(8)

OpenBSD includes httpd(8) in the base system. It is not based on Apache: it was written from scratch by OpenBSD developers with a small codebase and security-first design.

Reyk Floeter's httpd design paper documents the engineering decision. Keeping nginx in base required local hardening patches against a growing upstream codebase, while its custom allocators and replacements for libc routines interfered with OpenBSD's system defenses and made review harder. OpenBSD's httpd deliberately concentrates on static files, FastCGI, and TLS, uses the system allocator, and runs chrooted with privilege separation. Direct control of the base lets OpenBSD replace a respected upstream program when that program no longer fits the operating system's security architecture.

OpenBSD recently extended relinking hardening to userland network services such as httpd and smtpd. Randomized relinking changes internal object layout across builds and updates, which reduces gadget predictability and raises exploit cost in the same spirit as KARL and library-order randomization. This strengthens OpenBSD's broader model: keep privileged components small, audited, and less predictable to an attacker. See the OpenBSD -current changelog entry "Random-relink smtpd(8) and httpd(8) at boot" and the related OpenBSD community write-up: OpenBSD -current changelog, Undeadly article.

10.1 - relayd(8)

relayd(8) is OpenBSD's relay and application-layer proxy daemon. It provides reverse proxying, load balancing, health checks, and TLS handling with a compact configuration model that integrates well with the rest of the base networking stack.

10.2 - smtpd(8)

smtpd(8), from the OpenSMTPD project, is OpenBSD's native mail daemon in base. Its design divides SMTP reception, queueing, lookup, scheduling, control, and delivery among processes with distinct privileges, as documented in section 19 below.

11 - KARL

OpenBSD installs a kernel link kit during installation and upgrades. After each boot, reorder_kernel(8) relinks the kernel's object files in randomized order for the next boot. This technique, Kernel Address Randomized Link (KARL), changes internal addresses and gadget locations instead of randomizing only the kernel's base address. Library-order randomization applies the same principle to core userland libraries.

  • macOS, Windows, and Linux deploy KASLR, which randomizes the kernel's load address. KARL also changes the relative layout within the OpenBSD kernel. That extra interior randomization denies an attacker the stable object layout of a fixed kernel build.

12 - Kernel & Userland

The kernel and userland in OpenBSD, as in the BSD family generally, are developed together. The same project that introduces kernel features also controls the base userland, so new security interfaces propagate consistently across the OS. pledge, unveil, and arc4random demonstrate that integration.

That control extends well beyond kernel interfaces. OpenBSD maintains an unusual amount of commonly used system software itself. It chooses among writing, importing, forking, and substantially adapting a component according to interface clarity, maintenance burden, integration, and license suitability. The project's software and innovations history documents how substantial this work is.

This unified ownership is one of OpenBSD's strongest architectural advantages. Security-relevant daemons, libraries, and utilities share the base system's audit practices, privilege boundaries, defensive APIs, and documentation standards. Security is not the sole motive for every implementation; licensing, maintainability, correctness, and integration also determine what the project owns. The result is one review process across critical components.

OpenBSD developer Ted Unangst explicitly warned that starting over can replace one set of bugs with another and discard obscure lessons accumulated by mature code. The point is to control the anticipated future bug surface and maintenance burden by restoring only the functionality that is worth carrying. OpenBSD's willingness to ship less, understand more, and reject compatibility baggage is an advantage few operating-system projects exercise this consistently.

  • The Linux kernel and the GNU Core Utilities, or musl/BusyBox on non-GNU systems, are developed independently. That makes it much harder to introduce something like pledge, or even a consistent SELinux/AppArmor approach, across all base tools. This lack of unity makes Linux security fragmented. macOS and Windows have more unified development, but they tend to prioritize features and compatibility, especially Windows with its heavy legacy burden.

13 - LibreSSL

OpenBSD forked LibreSSL from OpenSSL in 2014 after Heartbleed exposed the cost of maintaining a sprawling TLS and cryptography stack. The documented project goals are exact: modernize the code so it is easier to audit, understand, and repair; remove obsolete or broken features and platform support; apply code review and frequent releases; and use secure programming interfaces. This is security work through deletion, simplification, and continuous maintenance, not a claim that a fork becomes defect-free.

LibreSSL develops libcrypto, libssl, and the smaller libtls API inside the OpenBSD source tree. The project also publishes portable releases for Linux, the BSDs, macOS, and Windows. Portability demonstrates that OpenBSD's implementation can benefit other systems without making unsupported claims about which TLS library a current macOS or Windows installation uses internally.

13.1 - openrsync(1)

openrsync is OpenBSD's BSD-licensed implementation of rsync. It synchronizes local and remote files and is compatible with rsync protocol version 27.

It is a clean-room, ISC-licensed implementation written by Kristaps Dzonsons. It began as part of rpki-client(8), which needed to retrieve RPKI repository data using the rsync protocol, and was imported into OpenBSD in 2019. This gave the base system an implementation under OpenBSD's direct integration, audit, and maintenance process and its preferred license, without importing the original GPL rsync code.

openrsync deliberately implements a smaller interface. The current manual defines its supported option set and compatibility with rsync protocol version 27. Its target is deliberately narrower than a complete replacement. OpenBSD's source tree also contains detailed descriptions of the rsync protocol and daemon handshake. These specifications let reviewers compare the implementation with documented wire behavior instead of treating the original program as the protocol's only description.

The strongest reason to prefer openrsync on OpenBSD, when its feature set is sufficient, is its use of native sandboxing. The current main.c uses pledge(2) to limit system operations and tightens the promises after network setup. On the receiving side, receiver.c applies unveil(2) around the source paths and destination root. In server mode, server.c seeds the protocol's MD4 hashes with arc4random(3) instead of the time of day.

The reduced option surface leaves less legacy behavior to understand and test, while the sandbox limits what a bug can reach. The available evidence does not establish that openrsync has fewer vulnerabilities than rsync. It is not a drop-in replacement for workflows that need newer protocols or unsupported options, and its ordinary client and server roles are not a separate privilege-separation design.

14 - License

You are free to use the operating system however you want, including for business, under ISC or Berkeley-style licenses. By project policy, GPL code is not acceptable for new additions. The BSD license is freer than the GPL, which places more restrictions on code use.

This licensing culture also helps protect the project from corporate capture and internal pressure. Linux has spent years pulled between community goals and large corporate interests, especially from companies such as IBM that want Linux shaped for enterprise platforms. That pressure damages the Unix philosophy.

A license as permissive as BSD allows companies to use, close, distribute, and resell OpenBSD code. I see that freedom as a strength, not a weakness, because it keeps the project simple and avoids the ideological battles that often surround copyleft licensing.

Licensing is not itself a security mechanism, but it shapes which implementations OpenBSD can bring into the base tree and maintain on its own terms. openrsync illustrates the practical effect: its ISC license, focused feature set, and OpenBSD-native sandboxing all fit the project's engineering model, whereas the license alone would not be a security argument.

  • The Linux and GNU ecosystem relies heavily on the GPL, while macOS and Windows are proprietary. OpenBSD instead publishes the complete operating-system source under permissive licenses that allow both commercial and noncommercial reuse.

15 - Malloc leak detection

OpenBSD's malloc(3) can record allocation call sites and emit a leak report through utrace(2). Deeper call stacks make debug symbols useful when mapping the report back to source. The same allocator exposes auditing options for canaries, guard pages, use-after-free detection, and stronger junking. These diagnostics find defects in native code; they are not runtime proof that an application is memory-safe.

  • Linux, macOS, and Windows have tools in their ecosystems for this, but none are integrated into the operating system by default.

16 - Documentation - manpages

OpenBSD documents the base system as one coherent product. Every binary, library, driver, or script delivered in base has a manual page, and the project treats missing documentation for a system function as a bug.

  • Linux documentation is fragmented by comparison, which leaves many users with major knowledge gaps and leads to configuration errors. That weakens security in practice. Community projects such as the Arch Wiki partly compensate for this gap.

Linux still falls short here.

17 - Meltdown and Spectre

OpenBSD disables simultaneous multithreading (SMT) by default. The policy addresses cross-thread information leakage demonstrated by speculative-execution and microarchitectural attacks; it is distinct from the page-table isolation used against Meltdown. Administrators can re-enable SMT through hw.smt when their performance needs and threat model justify sharing a physical core.

  • Fedora Secureblue sets mitigations=auto,nosmt, which disables SMT by default on processors affected by relevant vulnerabilities. OpenBSD disables SMT by default without making that decision conditional on the detected processor.

18 - Memory allocation randomization

Windows, Linux, macOS, and Android all provide system allocators. OpenBSD applies its hardened allocator and diagnostic behavior as the base-system default rather than as an optional replacement.

  • GrapheneOS's hardened_malloc is heavily inspired by OpenBSD's design and offers stronger hardening than typical Linux defaults. Fedora Secureblue uses hardened_malloc globally. But as the GrapheneOS devs themselves said:

    The main differences in the design are that it's solely focused on hardening rather than finding bugs

OpenBSD's allocator combines exploit resistance with diagnostics intended to expose memory errors during development. That design attacks both sides of the problem: it detects defects before release and makes surviving defects harder to exploit. It does not prove that the allocator contains fewer undiscovered bugs.

19 - OpenSMTPD

OpenSMTPD was written from scratch by OpenBSD developers. A simple mail daemon was needed for the base system, and there were no suitable alternatives. The goals are simplicity, security, and reliability under an acceptable license (ISC).

The OpenSMTPD project deliberately targets the majority of mail-server deployments instead of every obscure use case, combines strict network-input validation with an understandable configuration language, and treats every accepted message as data that must not be lost. Avoiding feature maximalism reduces what operators must configure and what developers must keep correct without reducing the daemon to a toy.

The security consequence comes from its process architecture. SMTP reception, lookups, queueing, scheduling, control, and delivery are divided among processes with well-defined jobs. They communicate through imsg(3), not shared memory; privileged work stays in the parent, most workers are unprivileged and chrooted, and the queue has a separate account. pledge(2) restricts each worker's allowed operations, while re-execution gives child processes memory layouts independent of the initial parent. A flaw in one role therefore does not automatically grant the authority or memory state of every other role. OpenBSD built the least-privilege boundaries into the MTA instead of trying to bolt them on afterward.

Extensibility does not require bloating that core. The smtpd-tables(7) interface places database and directory lookups in standalone processes outside smtpd(8)'s address space and allows them to run under different users. OpenSMTPD can therefore support site-specific backends without making all of their dependencies part of the daemon's memory-safety and privilege boundary. That is a better form of modularity than merely accumulating loadable features in one process.

OpenSMTPD's official security advisory history includes serious bugs, including command-execution flaws fixed in 2020. Process boundaries do not erase those bugs; they limit the authority assigned to each exposed role. That explicit division of responsibility is the architectural advantage.

  • OpenSMTPD has a portable version available in several Linux distributions, but it is not included by default in any of them.

20 - OpenSSH

OpenSSH is OpenBSD's most widely deployed software. It supplies SSH client and server implementations across BSD systems, macOS, Windows, network appliances, and cloud infrastructure. OpenSSH has selected a hybrid post-quantum key exchange by default since April 2022.

21 - Firewall

pf is OpenBSD's stateful packet filter. Its text rules support variables, lists, and tables, so an administrator can review matching, translation, and policy in one pf.conf. Commercial firewall appliances also use pf-derived code.

  • Linux splits packet filtering across the netfilter kernel framework, iptables or nftables rule syntax, and frontends such as firewalld and ufw. This layered policy surface is harder to inspect than one pf.conf; inconsistent frontend and native rules can also leave an administrator reviewing only part of the active policy.

  • Windows exposes its stateful firewall through Windows Defender Firewall with Advanced Security and PowerShell. It supports detailed policy, but its object and profile model is more verbose than pf's text rules and harder to review as one complete policy.

  • macOS ships pf for packet filtering, alongside a separate application firewall. The inherited pf grammar gives administrators a readable low-level policy language, although Apple's application firewall is not itself based on pf.

  • NetBSD's npf also provides stateful filtering with a declarative ruleset. Its grammar is similar to pf but exposes a different object and procedure model.

  • FreeBSD ships pf, ipfw, and ipfilter. Supporting three policy engines fragments documentation and administration, while FreeBSD's pf has diverged materially from current OpenBSD pf.

22 - PID randomization

OpenBSD assigns each new process a random unused PID. This removes the sequential predictability required by attacks that guess process IDs.

  • Linux kernel allocates PIDs in a semi-sequential (incremental) way, recycling when it reaches pid_max; it does not randomize them by historical design. The same goes for Windows and macOS.

23 - ping randomness

Both ping(8) and ping6(8) obfuscate transmitted monotonic clock values by offsetting them with a random value. ChaCha streams vary each payload. The random offset conceals the transmitted clock value, and varying payloads remove another stable fingerprint.

  • Other ping implementations make different payload and timestamp choices. The relevant OpenBSD property is concrete: its base utility deliberately removes stable timing and payload metadata instead of exposing it unchanged.

24 - pledge

pledge lets a program restrict its own permitted classes of system calls with a short declaration. After compromise, the process retains only the operations declared for its current execution phase. OpenBSD developers introduced pledge across most base programs within two releases and require new base programs to use it where applicable.

  • Linux has seccomp, which can emulate pledge's syscall-restriction part, but seccomp is low-level, hard to write correctly by hand, and brittle across libc/kernel behavior changes and needs tools (like libseccomp) to avoid mistakes; writing policies for this is error-prone.
  • I do not consider seccomp practically usable for ordinary hardening, and this critique explains why: Seccomp is unsafe at any speed
  • Windows has no direct pledge analogue. macOS has sandbox_init / Seatbelt, more integrated for GUI apps but more complex for arbitrary CLI programs.

25 - unveil

The unveil system call limits filesystem open calls to a defined set of paths. It extends the idea of pledge: simply limiting programs to open is insufficient, because open is valid for the whole filesystem.

A utility such as passwd(1) needs account files and specific runtime resources, not arbitrary access to a user's documents. Restricting its visible paths limits which files a compromised process can reach.

OpenBSD ports integrate pledge and unveil restrictions into browsers including Firefox and Chromium. The permitted paths and promises vary by browser version, features, and local configuration; the boundary removes direct access to unrelated files and system operations that the browser process does not need. A browser exploit still reaches everything permitted by that profile.

  • Linux provides Landlock for application-selected filesystem restrictions and AppArmor, SELinux, and Smack for externally managed policy. These mechanisms can enforce strong confinement, but they do not give ordinary programs the same compact, paired pledge(2)/unveil(2) interface. Distribution policy, application policy, and syscall filtering therefore remain separate layers, which makes the active boundary harder to inspect and deploy consistently.
  • Windows has no direct unveil analogue, nor does macOS.

26 - Privilege and user separation

OpenBSD applies privilege separation, dedicated accounts, chroots, or sandboxing across many base daemons and utilities. Examples include bgpd(8), dhclient(8), dhcpd(8), dvmrpd(8), eigrpd(8), file(1), httpd(8), iked(8), ldapd(8), ldpd(8), mountd(8), npppd(8), ntpd(8), ospfd(8), ospf6d(8), pflogd(8), radiusd(8), relayd(8), ripd(8), script(1), smtpd(8), syslogd(8), tcpdump(8), tmux(1), xconsole(1), xdm(1), X server(1), ypldap(8), pkg_add(1), etc.

  • All major operating systems support reduced service privileges. OpenBSD applies those boundaries directly in base-daemon architecture and reviews them in the same tree. Linux, macOS, and Windows distribute comparable controls across service managers, sandbox systems, access control policy, and per-service configuration.
  • Windows has restricted tokens, integrity levels, service SIDs, AppContainers, and process mitigations. Those controls are capable, but their policy is spread across several object models and administrative interfaces instead of one base-system daemon architecture.
  • Mainstream Linux distributions use reduced service accounts, namespaces, capabilities, seccomp, and mandatory-access-control policy to different degrees. OpenBSD's advantage is consistency: base daemons are designed and reviewed with those boundaries as part of the same source tree.

27 - Privilege revocation

Related to the work on privilege separation, some programs were refactored to drop privileges while holding onto a tricky resource such as a raw socket, reserved port, or modification-locked bpf(4) descriptor, for example ping(8), traceroute(8), etc.

  • Linux can combine capabilities, file descriptors, namespaces, and seccomp to retain a resource while dropping broader authority; macOS and Windows provide their own sandbox and restricted-token models. Their integration varies by program. OpenBSD performs this refactoring directly in base utilities and audits the resulting privilege boundary as part of the operating system.

28 - MAC addresses randomized

OpenBSD lets you use randomized MAC addresses via ifconfig.

ifconfig iwm0 lladdr random

Randomizing the link-layer address limits passive correlation by a local Wi-Fi network. It does not hide higher-layer identifiers, traffic patterns, accounts, or the device's radio characteristics, so it is one anti-tracking measure rather than network anonymity.

  • Linux network managers and privacy-focused systems such as Tails also support MAC-address randomization. Defaults and per-network behavior differ, so the active configuration matters more than the presence of a toggle.

29 - rcctl(8)

rcctl maintains OpenBSD's daemon settings in rc.conf.local. I prefer this narrow text-based control plane to systemd's combined service, logging, session, timer, network, and IPC architecture. The security argument is inspectability and limited scope, not a claim that a short command automatically makes its services secure.

Strictly speaking, rcctl is not OpenBSD's init system or a resident supervisor. The narrowly scoped init(8) is PID 1; it enters multi-user mode, manages terminal logins, and handles shutdown or the transition to single-user mode. It invokes the transparent rc(8) startup script, which performs housekeeping, raises the kernel securelevel, and starts the explicitly selected daemons through common rc.d(8) scripts. Separate components keep PID 1, boot policy, service scripts, and administrative configuration from sharing one resident implementation.

rcctl(8) is the small administrative front end for that design. It writes local choices to the upgrade-safe /etc/rc.conf.local file and can set a daemon's arguments, user, login class, routing table, working directory, logger, and timeout. It can also test configurations and expose enabled-but-failed or disabled-but-running daemons. There is no opaque service database to reconcile: the desired state remains inspectable as text, and services do not become enabled merely because a package installed a control script. The smaller control plane leaves the administrator's intent visible in one text configuration.

  • Gentoo and distributions such as Artix, Alpine, and Void have the advantage of avoiding systemd, or SysVinit in some cases. But Qubes OS, Fedora Secureblue, Tails, Whonix, Kicksecure, Arch, NixOS, and many others use it.

30 - recallocarray(3)

recallocarray(3) resizes arrays while checking the element-count multiplication for overflow. It clears newly allocated memory and explicitly discards memory that becomes unallocated, which makes it suitable for resizing buffers that hold keys or other secrets.

  • The exact function is an OpenBSD extension that has been ported through compatibility libraries. Other platforms offer overlapping allocator and explicit-clearing APIs, but ordinary realloc does not provide this combined contract.

31 - rpki-client(8)

The rpki-client(8) utility synchronizes RPKI repositories through a built-in HTTPS client and openrsync(1). It validates certificates, manifests, revocation lists, and signed objects beneath configured Trust Anchors, then emits Validated ROA Payloads, BGPsec Router Keys, and Validated ASPA Payloads for routing software. This is the operational context that originally required OpenBSD to implement the rsync protocol without importing the GPL rsync code.

  • This is an OpenBSD feature. It is available for installation on Linux and macOS, although no Linux distro uses it by default.

32 - Sane & secure defaults

OpenBSD ships with sane, secure defaults in daemons and configurations.

The system is intended to be secure by default, and many of its security features are either missing or optional in other operating systems.

A fresh installation therefore starts from a deliberate security baseline instead of enabling a broad service set and asking the administrator to remove it. Base daemons such as sshd(8) ship with project-maintained privilege boundaries and conservative defaults. Threat-specific authentication, network, and access policy still belongs to the administrator.

  • Linux distributions assemble security policy from kernel settings, service overrides, package choices, and optional mandatory-access-control systems. Secureblue supplies a stronger default policy than mainstream desktop distributions, but it still hardens an independently developed kernel and userland. OpenBSD defines defaults across an integrated base system. Ad hoc Linux hardening creates another policy layer for administrators to audit; contradictory sysctls, service overrides, and access-control rules can break updates or silently leave gaps.
  • Secureblue demonstrates that a Linux distribution can ship a much stronger desktop policy than mainstream defaults. GrapheneOS applies an even more integrated hardening model to Android. Neither controls one kernel-and-base source tree in the OpenBSD sense.

33 - signify(1)

signify signs and verifies files through a deliberately narrow key and command model. OpenBSD has used it for release signatures since 5.5 and for syspatch binary patches. Its original design uses Ed25519 and excludes OpenPGP's packet, certificate, and key-management machinery.

Ted Unangst's signify design presentation explains why this narrowness matters. OpenBSD needed to sign and verify release artifacts, not import PGP's algorithms, packet formats, key-management models, and dependency graph. signify chose one reviewed signature primitive and a tiny operational interface. That makes the code and the trust path from an installed system to its next installer far easier to audit. It is another case where OpenBSD's smaller implementation is superior precisely because it refuses functionality the base system does not need.

The same applies to packages: when a package is signed, pkg_add uses the appropriate key in /etc/signify to verify the signature and installs it only when the signature and checksums match. A repository compromise alone cannot substitute modified artifacts without detection; compromise of the corresponding signing key remains outside that guarantee.

  • Linux distributions commonly use GnuPG/OpenPGP. signify excludes multiple signature algorithms, subkeys, certificate expiry rules, and legacy packet formats because OpenBSD release verification does not need them. Fedora integrates OpenPGP package verification well, but it retains the broader format and key model.
  • GnuPG/OpenPGP is large and complex; signify is simple and secure by default on OpenBSD.
  • Signify is available for installation on Linux and macOS.

34 - Stack

Since OpenBSD 7.3, the kernel places the stack at a random location in the upper quarter of userland virtual address space, providing up to 26 additional address bits. This applies to 64-bit architectures except alpha. The additional entropy makes the stack address harder for an exploit to derive.

  • Linux distributions can add independent stack-layout and kernel hardening measures, and grsecurity supplies additional mitigations. OpenBSD's distinction here is a documented base-system policy applied by its own kernel and runtime rather than an administrator-selected patch set.

35 - stack-register checking

A memory mapping should receive only the permissions and role it needs. OpenBSD's MAP_STACK flag marks mappings intended for use as stacks. On system-call entry, the kernel opportunistically verifies that the stack-pointer register refers to a stack mapping and kills a process that has pivoted it into ordinary data memory. This tightens the ABI against a technique used in return-oriented attacks.

  • macOS, Windows, and Linux: No.

36 - Swap encryption by default

OpenBSD encrypts swap with a randomly generated key by default. This prevents plaintext memory pages, including credentials and application secrets, from persisting on the swap device after shutdown.

  • Linux supports encrypted disk-backed swap, while many desktop distributions now use compressed RAM through zram instead of a swap partition. The deployed protection depends on the distribution and installation; no single Linux-wide default exists.
  • GrapheneOS follows Android's different storage and memory model, so its protections are not a direct comparison with encrypted on-disk swap.
  • macOS swap and sleep image are encrypted when FileVault (full-disk encryption) is enabled. I rate Windows BitLocker poorly for reliability.

37 - Syscall origin verification

The kernel and dynamic linker register the precise instruction addresses of each system-call stub through pinsyscalls(2). The kernel then rejects a system call made from any other address. Injected code cannot issue raw system calls from an arbitrary executable page; it must first reach the registered stub for the requested call.

  • Linux, Windows, and macOS: No.

38 - unwind(8) validating DNS resolver

unwind is a validating DNS resolver. It is designed for client machines such as workstations or laptops and listens only on localhost. It queries nameservers directly and can switch to resolvers learned through network autoconfiguration when the local network blocks direct DNS. It periodically probes the network and switches back when direct resolution works again. This keeps validation and caching under local control while preserving connectivity on restrictive networks; it does not hide DNS traffic or guarantee resolver privacy.

  • Fedora Secureblue uses unbound, which OpenBSD also includes in base. unbound serves broader recursive-resolver deployments; unwind gives client systems a smaller adaptive resolver, so the same desktop policy requires less configuration.

39 - W^X Memory

Since 2003, OpenBSD's W^X policy has prevented memory from being both writable and executable without an explicit exception. Since OpenBSD 6.0, an executable that needs such mappings must carry PT_OPENBSD_WXNEEDED and reside on a filesystem mounted with wxallowed. An attacker cannot simply write an injected payload into ordinary data memory and execute it from the same mapping.

  • Linux, Windows, and macOS all deploy non-executable memory and can enforce stronger code-generation policy for selected processes. OpenBSD's distinction is its strict base-system W^X rule and explicit executable-and-filesystem exception model.

40 - WireGuard

OpenBSD includes the wg(4) WireGuard driver and ifconfig(8) control interface in the base system. WireGuard deliberately fixes a small suite of cryptographic primitives and a narrow key-based configuration model, avoiding cipher negotiation and a large protocol option surface. Kernel integration removes a package dependency and places the implementation under the same review and release process as the rest of OpenBSD networking. It does not make a VPN provider trustworthy or conceal endpoint metadata by itself.

  • WireGuard is integrated into the OpenBSD kernel. Linux, Windows, and macOS have WireGuard support, but not in this OpenBSD-style base system form.

41 - file(1)

file(1) is sandboxed and runs as the _file user. Imagine downloading a random file from the internet and analyzing it with file. If file had a local code execution bug and the downloaded file was crafted to exploit it, that bug could become dangerous. OpenBSD reduces this risk by sandboxing and chrooting the utility by default.

  • The mechanism is not merely available as an optional sandbox: OpenBSD ships file(1) with this restricted account and filesystem boundary in the base system.

42 - vmm(4) - compartmentalized hypervisor

Theo de Raadt has long criticized virtual machines and their security model, arguing that hypervisors add a high-value attack surface. OpenBSD nevertheless created a native hypervisor with a narrow feature set and little device emulation compared with general-purpose virtualization stacks. It omits:

  • Graphics
  • Snapshots
  • Guest SMP support
  • Hardware passthrough
  • Live migration across hosts
  • Live hardware change

Supported guest operating systems are currently limited to OpenBSD and Linux. Because there is no VGA support yet, the guest OS must support a serial console. Graphical access requires separately configured tools such as Xephyr or a remote framebuffer; vmm does not supply a virtual graphics adapter.

The native stack implements this narrow scope by separating the vmm(4) kernel monitor, the vmd(8) userland daemon, and the vmctl(8) client. Device emulation stays primarily in userland, and vmd creates a separate VM process for each guest instead of putting every guest's device parsers directly in the host kernel.

Dave Voutila's paper on hardening vmd's emulated devices identifies the threat: emulators consume attacker-controlled guest data and are a recurring source of VM escapes. vmd uses fork-and-exec privilege separation, dedicated process roles, reduced user and group IDs, filesystem restrictions, and pledge(2). OpenBSD 7.4 then introduced a multiprocess model for emulated VirtIO block and network devices, adding another boundary between a compromised device emulator and the rest of vmd(8) or other device code.

The missing features reduce the emulation, passthrough, and migration paths that OpenBSD must maintain and expose. The FAQ does not identify security as the motive for every omission. The host trust boundary still includes vmm(4), vmd(8), and the kernel; an exploitable bug there can cause an escape. OpenBSD's advantage is direct project control over this compact stack and consistent process isolation throughout userland device emulation.

  • QEMU/KVM, Xen, Hyper-V, VMware, and VirtualBox support broader hardware models, management APIs, snapshot formats, passthrough, or migration. Those capabilities serve valid deployments, but they also add parsers, privileged interfaces, and state transitions that vmm does not carry.
  • Hardware passthrough exposes the host to device DMA and reset behavior. An IOMMU constrains DMA, but the device, firmware, and passthrough path still enlarge the trusted computing base. vmm avoids that class of configuration by not supporting passthrough.

43 - X server without root permissions and xenodm: the secure X Display manager

Since 2014, OpenBSD's X server no longer requires special privileges and can be run as a regular user rather than root. OpenBSD has its own soft fork of the X.Org server called Xenocara, where the project maintains its local integration and hardening changes. The base display path also disables the X server's remote TCP listener, removing an unnecessary network entry point.

Xenodm is a simplified fork of xdm. It removes XDMCP and retains the BSD Authentication path used by OpenBSD, eliminating code and remote protocol surface that the base display manager does not need. It is the supported path for starting the unprivileged X server without restoring setuid root to Xorg.

  • The standard X11/Xorg stack carries decades of protocol and compatibility code. Xenocara gives OpenBSD direct control over its local patches, unprivileged execution, authentication, and network policy. XLibre is a later X server fork available on Linux, but it does not inherit OpenBSD's kernel, privilege, and base-system integration.

Wayland removes X11's default ability for one client to inspect or inject input into every other client, but the compositor, protocols, portals, and XWayland compatibility server still define the effective boundary. Fedora Secureblue disables XWayland by default and excludes compositors such as Hyprland when their security model does not meet its policy. Xenocara and XLibre instead harden and maintain an X11 stack; only XLibre is available on Linux.

44 - No proprietary blobs

OpenBSD does not place non-free firmware in its installation media or source tree. The fw_update(8) utility can fetch separately distributed firmware required by supported hardware. This keeps the base system redistributable without pretending that modern devices operate without proprietary firmware.

  • Mainstream Linux distributions install redistributable firmware alongside the kernel. Linux-libre distributions such as Hyperbola, Trisquel, and Parabola remove the corresponding blobs and loading requests, often at the cost of hardware support.
  • Windows and macOS are proprietary software.
  • FreeBSD and NetBSD make different firmware choices in their base systems and packages. The relevant OpenBSD distinction is its clean separation between the redistributable OS and firmware fetched for specific hardware.

45 - RETGUARD

RETGUARD is a replacement for the stack protector that uses a per-function random cookie (located in the read-only ELF .openbsd.randomdata section) to consistency-check the return address on the stack. Implemented for amd64 and arm64 by Todd Mortimer in OpenBSD 6.4, for mips64 in OpenBSD 6.7, and powerpc/powerpc64 in OpenBSD 6.9. amd64 system call stubs also protected in OpenBSD 7.3.

  • Linux and macOS: No.
  • Windows utilizes CFG, DEP/NX, Control Flow Application Technology (CET) support on newer CPUs (hardware shadow stacks), and SEH/unwind metadata. Hardware shadow stacks and RETGUARD both protect backward control flow, but enforce that property through different hardware and software mechanisms; their coverage depends on architecture and deployment.

46 - Audit Process

OpenBSD security page

The process we follow to increase security is simply a comprehensive file-by-file analysis of every critical software component. We are not so much looking for security holes, as we are looking for basic software bugs, and if years later someone discovers the problem used to be a security issue, and we fixed it because it was just a bug, well, all the better. Flaws have been found in just about every area of the system. Entire new classes of security problems have been found during our audit, and often source code which had been audited earlier needs re-auditing with these new flaws in mind. Code often gets audited multiple times, and by multiple people with different auditing skills.

Some members of our security auditing team worked for Secure Networks, the company that made the industry's premier network security scanning software package Ballista (Secure Networks got purchased by Network Associates, Ballista got renamed to Cybercop Scanner, and well…) That company did a lot of security research, and thus fit in well with the OpenBSD stance. OpenBSD passed Ballista's tests with flying colors since day 1.

Another facet of our security auditing process is its proactiveness. In most cases we have found that the determination of exploitability is not an issue. During our ongoing auditing process we find many bugs, and endeavor to fix them even though exploitability is not proven. We fix the bug, and we move on to find other bugs to fix. We have fixed many simple and obvious careless programming errors in code and only months later discovered that the problems were in fact exploitable. (Or, more likely someone on BUGTRAQ would report that other operating systems were vulnerable to a newly discovered problem, and then it would be discovered that OpenBSD had been fixed in a previous release). In other cases we have been saved from full exploitability of complex step-by-step attacks because we had fixed one of the intermediate steps. An example of where we managed such a success is the lpd advisory that Secure Networks put out.

47 - Project Goals

OpenBSD's goals are clear, precise, and they greatly increase user confidence.

OpenBSD project goals

  1. Provide the best development platform possible. Provide full source access to developers and users, including the ability to look at CVS tree changes directly. Users can even look at our source tree and changes directly on the web!

  2. Integrate good code from any source with acceptable licenses. ISC or Berkeley style licenses are preferred, the GPL is not acceptable when adding new code, NDAs are never acceptable. We want to make available source code that anyone can use for ANY PURPOSE, with no restrictions. We strive to make our software robust and secure, and encourage companies to use whichever pieces they want to. There are commercial spin-offs of OpenBSD.

  3. Pay attention to security problems and fix them before anyone else does. (Try to be the #1 most secure operating system.)

  4. Greater integration of cryptographic software. OpenBSD is developed and released from Canada and due to Canadian law it is legal to export crypto to the world (as researched by a Canadian individual and as documented in the Export Control list of Canada).

  5. Track and implement standards (ANSI, POSIX, parts of X/Open, etc.)

  6. Work towards a very machine independent source tree. Support as many different systems and hardware as feasible.

  7. Be as politics-free as possible; solutions should be decided on the basis of technical merit.

  8. Focus on being developer-oriented in all senses, including holding developer-only events called hackathons.

  9. Do not let serious problems sit unsolved.

  10. Make a release approximately every six months.

Published goals, a public CVS history, and a regular release cadence make the project's priorities and changes inspectable. Security claims can therefore be checked against source history and shipped behavior.

  • Linux distributes authority among the kernel, GNU and non-GNU userlands, distributions, service managers, and corporate-funded upstream projects. That model has no single base-system goal or audit boundary comparable with OpenBSD's.
  • Windows has centralized development, but Microsoft also preserves extensive application, driver, directory, and enterprise-management compatibility. Those commitments retain interfaces and code that OpenBSD is willing to remove.
  • macOS also has centralized development, but its source and security policy are only partly public. Users can observe shipped behavior, not review the complete system or its decision process.
  • NetBSD and FreeBSD also have clear goals, although almost completely different from OpenBSD.

48 - Politics-free

Be as politics-free as possible; solutions should be decided on the basis of technical merit.

OpenBSD states technical merit and freedom from politics as project goals. Its public development record, including Theo de Raadt's responses on the mailing lists, applies that rule directly rather than presenting it as an empty slogan.

A documented example occurred when an OpenBSD user proposed a change of term in the OS code, claiming that the term was sexist against women and was "pretty offensive": OpenBSD advocacy mailing list: proposed terminology change

But OpenBSD creator Theo de Raadt responded: Theo de Raadt's response on the mailing list

In that exchange, the project rejected the proposed terminology change because its maintainers did not accept the technical case. That decision follows the published goal quoted above; it does not require a broader claim about every decision the project has made.

  • Linux, by contrast, often tries to satisfy social expectations before focusing on software efficiency and security. Vanity and public approval sometimes matter too much in the Linux world, while old bugs and structural problems remain unresolved.

    One example is the merge of inclusive-terminology rules into the Linux kernel tree, aimed at replacing terms such as "master", "slave", "blacklist", and "whitelist" that programmers had used for decades: Linux Reviews article

  • The terminology rule is a governance choice, not a security or performance mechanism. My criticism is about priority: review time spent on vocabulary does not fix kernel defects or reduce attack surface. The linked commit establishes the policy change; the judgment about priorities is mine.

  • Beyond the kernel, the Linux world has cases like systemd "detect-fash":

    • systemd pull request #39285 (changed files)
    • The Register forums: Framework Linux controversy

The systemd proposal is more serious than a terminology rule because it would have changed runtime behavior according to a political label. The linked review records the proposal and its reception. I treat that willingness to encode political classification in system software as a trust failure, regardless of whether the patch ultimately ships.

OpenBSD's unified kernel and userland do not mechanically prevent a political decision. The stronger evidence is governance: the project publishes technical merit as a goal, conducts development in public, and rejected the cited proposal on that basis.

  • Windows and macOS also try to please broad audiences rather than focusing purely on software efficiency. That is understandable for proprietary, paid operating systems. I expect it there; I do not want it in Linux.

  • I view parts of the FreeBSD community as moving in the same direction, but I have not established a corresponding change in FreeBSD's technical decisions. Community culture and source-tree policy are separate claims.

  • I have not examined enough NetBSD or DragonFlyBSD governance records to make the same claim about them. Their absence from this comparison is a limit of my evidence, not evidence that the issue does or does not exist there.

49 - Less attack surface

OpenBSD publishes an integrated src tree for its kernel and base userland and a separate xenocara tree for X. A reproducible line-count comparison would have to fix the revision, file types, generated files, imported components, and architecture scope for every system. Raw totals that omit those choices create false precision. The defensible comparison is architectural:

  • A Linux distribution combines an independently developed kernel with a much larger collection of upstream packages. Debian's live source statistics report more than a billion source lines across the archive. That archive is not the code installed or reachable on one machine, but it illustrates the ecosystem and maintenance scope from which deployments are assembled.
  • OpenBSD's base tree deliberately excludes many drivers, compatibility layers, services, and administrative frameworks found in broader systems. What is absent cannot expose a parser, privileged interface, or dependency edge.

Windows and macOS do not publish source trees that permit the same current line-count comparison. FreeBSD and NetBSD publish their source, but a fair comparison requires matching generated files, imported code, architectures, and userland scope. I therefore do not attach an unverifiable number to those systems.

Source lines are not identical to remotely reachable attack surface, and a line count says nothing by itself about code quality. Scope still matters: every parser, compatibility path, driver, and privileged subsystem adds behavior that must be maintained and reviewed. OpenBSD's minimalism removes entire classes of such behavior instead of assuming that mitigations can make unlimited complexity harmless.

A complete Linux distribution adds a package set and independently maintained userland to its kernel. Not every installed line is reachable by an attacker, but a broad deployment carries more code, dependency edges, and separately governed security policy. Windows and macOS are harder to quantify because their complete corresponding source trees are not public.

OpenBSD starts with a smaller, more coherent base than mainstream general-purpose operating systems. That reduces the code and interfaces covered by each audit and makes system-wide mitigations easier to apply. The tradeoff is narrower hardware support, application compatibility, and feature coverage. For a security-first system, I consider that trade decisively superior.

The official OpenBSD websites express the same preference in a form visitors can inspect directly: mostly static HTML, no client-side application framework, and no analytics payload. That design avoids the third-party scripts, browser storage, and telemetry common on major technology websites. Minimalism improves privacy because the site simply does not ship those mechanisms.
